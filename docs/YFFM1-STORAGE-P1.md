# YFFM1 P1 存储优化

完成日期：2026-11-04。仅在本地隔离存档测试，未连接或部署至阿里云服务器，未迁移真实玩家数据。沿用 P0 的引用图回收、备份保留期和日志分段合并。

## 已完成

| 项目 | 实现 |
| --- | --- |
| 总决赛脱离 core | `season-final-index.json` 保存赛事状态、比赛摘要及独立战报引用；普通比赛和总决赛使用不同战报目录，即使 ID 相同也不会覆盖 |
| 完整战报压缩 | 新写入的已完赛战报和赛季归档使用 gzip level 3，保留完整事件、球员数据、战术复盘及回放；进行中的比赛仍使用原 live/checkpoint 路径 |
| 按需读取 | 启动只读取比赛索引；摘要中保存详情、引擎、战术复盘和回放标记。普通历史列表及总决赛对阵图不再附带整批正文，原比赛详情接口继续提供完整内容 |
| 有界缓存 | 同时限制 16 个记录和 8 MiB 解压 JSON 字节；超大归档读取后不进入缓存。LRU 命中仍核对文件状态；调用方获得的战报视图修改时才复制，归档返回独立副本 |
| 减少保存冗余 | JSON 分片比较与落盘共用一次序列化结果；逐卡片/玩家卡包/球队邮件跟踪深层修改，跳过未变玩家的分片序列化和原文件全文比较；非代理状态保留完整比较路径 |
| 故障与兼容 | 读取旧 schema 1，写入 schema 2；迁移前保存旧 manifest；失败保存恢复日志游标和分片缓存，重试避开未提交目录；缺失已提交索引触发备份读取，避免默认为空赛事 |

比赛算法、阵型规则、资产、钱包及奖励计算未变，前台渲染文件未在本轮修改。总决赛接口移除前台未使用的内嵌 `report`，保留比赛摘要、对阵节点和原详情入口。

## 本机对比

对照是本轮 P1 前、已包含 P0 修复的存储实现。Windows / Node 24.22.1 / i7-14700KF；真实球员重特性 V3 球队生成 5 份完整战报，平均 124,303 字节，正式比赛设置 `dotReplay=false`。以下不是线上容量或并发承诺。

| 相同隔离样本 | P1 前 | P1 后 |
| --- | ---: | ---: |
| 160 场当前赛季存档的当前引用字节 | 19,973,927 | 2,941,817（减少约 85.3%） |
| 新进程读取该存档 | 104.1 ms | 9.9 ms |
| 读取后的堆内存增量 | 25.02 MiB | 0.25 MiB |
| 列表读取后解码的战报数 | 启动已解析全部 160 份 | 0 |
| 顺序查看全部详情、回到事件循环并 GC 后的堆内存 | 29.62 MiB | 7.80 MiB |
| 12 份总决赛战报对应的每次 core 文件 | 1,554,666 B | 65,609 B（减少约 95.8%） |
| 12 次赛后保存并完成 P0 回收后的样本目录 | 3,110,921 B | 347,649 B |
| 120 次单玩家操作的球员卡分片序列化候选 | 1,200 次 | 119 次；第一次值未发生变化 |
| 同样操作的卡包/邮件分片序列化候选 | 各 1,200 次 | 各 120 次 |
| 上述操作保存 p50 / p95 | 24.1 / 25.1 ms | 18.5 / 20.1 ms |

详情首次读取需要解压，本样本约 1.6 ms；原实现启动已预读，所以相应访问约 0.004 ms。成本从所有列表/启动转移到实际详情请求。

同步读取一整批详情时会产生临时对象，WeakRef 视图到下一轮事件循环才可能回收。优化后该样本批量读取期间堆约 36.2 MiB，不能把 8 MiB 缓存限制解读为整个进程的内存上限。解析对象比 JSON 字节占用更大，响应、进行中的比赛和调用方持有的视图也另占内存。

保存耗时受 Windows 文件同步影响：仅 12 次总决赛后保存这组样本，p95 为 22.0 → 26.6 ms，未显示延迟改善；另一轮同样样本为 35.1 → 22.4 ms。减少的写入量和序列化次数是确定结果，不能保证每次磁盘同步延迟都下降。没有取消 fsync 或降低持久化保证。

原始比较：`outputs/storage-p1/comparison.json`。基准始终使用临时目录并校验资产/账本重载一致。

## 格式、旧数据和恢复

Manifest `schemaVersion=2` 指向普通比赛索引、总决赛索引及压缩报告。程序同时读取旧 `.json` 和新 `.json.gz`；现有 schema 1 存档第一次保存会先备份旧 manifest，再写入 schema 2。未变化的旧战报/归档可继续引用原文件，不在开包/交易请求中一次性转换所有旧战报。

完整转换用下方离线工具。它逐条校验逻辑内容摘要，覆盖联赛战报、总决赛战报、完整归档及其余业务状态；转换前后哈希一致才报告成功。单 JSON 存档仍走原读写路径，需要先用已有 `devtool/migrate-league-to-shards.js` 导出到新分片目录。

备份是 manifest 加它引用的全部文件；只复制一个 manifest 无法跨机器恢复。迁移前备份继续保护旧的未压缩文件，因此磁盘总占用不会立即下降到“当前引用字节”。P0 的迁移/管理备份 30 天到期并回收后，旧文件才有资格释放。

旧版本程序不支持 schema 2。回滚必须在停服状态下恢复迁移前 manifest **及其完整引用集合**，然后使用旧程序；这会回到该恢复点，迁移后的业务写入不会自动反向合并。新版可继续读取旧格式。不要只改版本号或直接删除旧 revision。

懒加载不会在启动时解压每份战报检测正文损坏；缺文件会报错，压缩正文损坏在详情读取时明确报错。离线完整转换/校验会读取全部记录，不会丢弃损坏正文后假报成功。

## 测试与操作命令

PowerShell 本地核心回归（所有账户、联赛、内容覆盖和卡牌编辑数据均隔离到临时目录）：

```powershell
cd D:\Yangfan\YFFM\YFFM1
node scripts/run-tests.mjs storage-p1.test.js storage-policy.test.js shard-compaction.test.js league-shards.test.js league-shard-safety.test.js season-final-tournament.test.js
```

手动进入游戏：`node server.mjs`，访问终端显示的地址。

以下命令把 `ROOT` 替换成实际分片目录。默认只读分析：

```sh
node devtool/optimize-league-storage.js ROOT
```

**停服后**，先保留可恢复副本，按分析结果的实际 revision 执行，例如 revision 为 123：

```sh
node devtool/optimize-league-storage.js ROOT --apply --offline --expected-revision=123
```

可指定 `--backup-dir=PATH` 和 `--service=NAME`。`--offline` 表示操作者已经停服；Linux 还会检查指定 systemd 服务。维护锁只约束该工具，不能替代停服，不能和游戏写入进程并行操作。中断后若留下 `.storage-maintenance.lock`，先确认工具和服务均未运行，再处理锁及恢复点。

转换保留旧引用，不会立即强制 GC。先验证比赛详情、资产和备份恢复，再使用原只读审计及回收工具；自定义备份路径必须在审计、转换和回收时一致。

## 验证范围和后续

15 个相关测试文件合计 **233 项通过**，覆盖旧格式转换及回滚、深层战报编辑、数组增删、缓存隔离与上限、嵌套卡片修改/转移、卡包和邮件分片、失败重试、缺索引恢复、重复压实、资产与免费装饰、历史详情、俱乐部和荣誉系统。实际总决赛比赛完成后，验证重载、摘要零解压及完整归档一致。

另用真实本地 HTTP 临时分片：10 账号、9 支玩家球队，20 个普通包和 3 个三选一包，新增 23 张卡；钱包保持一致，GC 前后资产与账本一致，重启恢复一致，无缺失引用。512 MiB V8 堆上限下进程 RSS 约 153 MiB，保存 p95 18.3 ms；这不是 2GB 云主机压力测试。结果：`outputs/storage-p1/sharded-http.json`。

P2 的结束交易/回收卡片审计归档、计算 Worker 和数据库评估仍未实施。重新开服后需实际采集阿里云磁盘、RSS、接口延迟和事件循环延迟，评估剩余瓶颈。
