# YFFM1 俱乐部系统深化评估

日期：2026-11-04。基于当前工作区实际代码。本文是功能与实施方案评估，没有修改球迷、门票、赞助、金币或比赛规则。

## 1. 产品范围与判断

世界杯、国家队、主教练卡及合同已由用户明确永久废弃，不会作为本轮俱乐部建设内容；现有赛后自动复盘继续保留。

**当前俱乐部已经有展示、收入和长期资产，但尚未形成完整的经营决策。** 更适合深化为“俱乐部身份 → 球迷与需求 → 球场与商业选择 → 赛事收入 → 财务复盘 → 下一季投资”的循环，而不是再增加一套直接抬高球员能力的数值系统。

建议先补财务和合同信息，再建设球迷/票务，最后加入少量有取舍的长期项目。沿用现有“球队建设 / 荣誉室”入口和风格，按需扩展内容，不要求重新设计主导航或其他页面。

## 2. 当前功能与缺口

| 领域 | 当前真实实现 | 完整度判断 | 需要补足的内容 |
| --- | --- | --- | --- |
| 俱乐部身份 | 队名、队徽/外观体系、球场名、冠名、队史荣誉 | 已有基础 | 冠名和原始队名的统一展示，长期发展履历 |
| 球场外观 | 看台、草皮、背景、转播场地与广告 | 基本闭环 | 外观权益与经济效果清楚区分；资源按需加载 |
| 球场容量 | 初始 30,000，10 档扩到 80,000，每次 5,000 座 | 基本闭环、选择较单一 | 真实需求、投资回收预测、经营代价 |
| 门票 | 正式主场收入，按比赛 ID 去重，写金币流水及赛后邮件 | 结算已闭环、经营较浅 | 收入解释、赛季汇总、需求/定价策略 |
| 上座率 | 普通 82%，购买流星看台后 100% | 固定公式 | 独立的球迷需求，不应单凭新增座位自动增加同等比例观众 |
| 赞助 | 正式赛后 35% 概率报价；普通/球场冠名/球队冠名 | 基本闭环 | 主动可选合同、报价有效期、续约、履约及现金流选择 |
| 财务 | 共用玩家金币钱包，有逐笔 ledger | 底层存在，玩家经营视图不足 | 分来源报表、赛季净收入、投资回收、预计而非保证收益 |
| 球迷关系 | 初始化会删除旧 supporters / attendance 字段 | 当前没有独立系统 | 小而稳定的球迷状态、需求和反馈 |
| 建设过程 | 扩容立即扣费并永久生效 | 只有结果 | 是否引入项目进度/机会成本应单独设计；不建议堆实时倒计时 |
| 赛季经营目标 | 赞助种类按排名门槛开放，荣誉另有归档 | 缺独立经营目标 | 多路径目标及季末总结，降低只看胜场的单一路径 |

没有工资、青训、教练组等系统，不应简单算作“漏做”。当前产品是足球卡牌经营与战术赛事，应优先补足已有循环，避免变成另一套高负担经理模拟。

## 3. 现行数值说明了什么

以下均由当前规则计算，不是拟定的新价格。只计算联赛主场、无杯赛/总决赛、无贴现和其他收入，用来解释现有经营深度，不能作为实际赛季收益承诺。

### 3.1 门票与扩容

现行公式：

```text
观众数 = floor(容量 × 上座率)
单场门票收入 = floor(观众数 × 0.08)
```

| 场景 | 主场收入 | 相对上一档增量 | 投资 | 简单回收所需主场 |
| --- | ---: | ---: | ---: | ---: |
| 初始 30,000 座、82% | 1,968 | — | — | — |
| 首次扩到 35,000 座、82% | 2,296 | +328 | 4,000 | 约 12.2 场 |
| 最后一次 75,000 → 80,000 座、82% | 5,248 | +328 | 26,000 | 约 79.3 场 |
| 30,000 座购买流星看台，82% → 100% | 2,400 | +432 | 20,000 | 约 46.3 场 |
| 80,000 座购买流星看台，82% → 100% | 6,400 | +1,152 | 20,000 | 约 17.4 场 |

全部扩建成本合计 127,000；30,000 到 80,000 座的普通门票增量为每主场 3,280。18 轮双循环联赛通常有 9 个主场；是否值得扩建主要取决于能玩多少后续赛季和金币机会成本。

**问题是容量和需求没有分开。** 扩容后固定 82% 的新增座位也能带来观众，容量本身近似同时创造需求。后期扩容虽然更贵，仍缺乏“球迷不足，暂缓扩建”的经营局面。没有维护、项目或需求约束时，决策主要是先买卡/强化还是先投资。

流星看台当前也包含明确的满座经济权益，不能只当作装饰品。后续引入球迷模型必须处理老玩家已购权益，不能在性能重构中取消。

### 3.2 赞助

- 每场正式赛事结束后，对真人球队有 35% 概率产生报价；待处理上限 5 份。
- 普通赞助最多 3 家，球场冠名和球队冠名各最多 1 家。
- 类型门槛：普通前 10、球场冠名前 6、球队冠名前 3。
- 当前按类型单季基数 5,000 / 15,000 / 30,000，乘报价期限形成一次性签约奖金；生成期限为 1–3 个赛季，合同跨真实赛季递减。
- 签约立即拿到整个奖金，没有周期履约付款或赛季目标；报价待处理状态没有明确到期时间。

**现状更接近随机奖励与有限槽位管理。** 同类合同金额主要随期限线性增长，玩家可控的商业路线较少；强排名又同时带来更高类型赞助，可能放大强队收入，需要与赛事奖励、门票和培养支出一起评估。

### 3.3 赛季时间与钱包

正常 `resetDailyCompetitions` 保留钱包并推进赞助期限；另一个后台 `resetCompetition` 路径会把钱包重置为初始值，并清空当前流水。两者不能混用为同一种“新赛季”。

拟建长期经营系统前，应确定：日常跨季、后台重赛/新赛季、完全重置分别保留什么。回收期和累计利润必须按正确路径统计；历史财务快照应在流水清理前形成。

## 4. 推荐的功能结构

### A. 俱乐部财务中心——第一优先，不先改经济

**玩家解决的问题：** 钱从哪里来、花到哪里、为何能/不能投资。

第一版即可从现有 ledger 和比赛记录生成：

- 当季、上季及近几季收入/支出，分别列门票、赞助、赛事奖励、市场净额、卡包/强化、X、建设、镜像等。
- 俱乐部经营与球员资产花费分项展示，仍共用原钱包，不引入第二种货币或另一本余额账。
- 主场逐场观众、收入和容量；扩容前后比较及预计回收场次。
- 活跃合同的剩余期限、签约已收金额、预计到期；一次性收入与持续收入分开。
- 赛季结算后的经营总结，并明确特殊后台操作造成的数据重置。

**完整度验收：** 报表能追溯到流水，分项之和与总额相符；转账的流入/流出不被误当成新创造金币；重复结算和重载不会重复记账。预估收益与已实现收益有明确区别。

**成本控制：** 在业务入账时更新汇总，或按流水 revision 缓存；不在每次完整联赛视图里扫描全部历史。详情按需读取，保持现有页面和操作响应。

### B. 球迷与票务——把球场变成经营选择

**推荐的最小状态：** 球迷基数、支持度、稳定声望，以及上季需求基线；不同时加入十几个相互影响的隐藏指标。

**推荐的规则方向：**

```text
需求 = 稳定球迷需求 × 票务策略 × 赛事/对手吸引力 × 有界状态修正
实际观众 = min(容量, 需求)
门票净收入 = 门票收入 - 已明确的相关成本（若未来启用）
```

数值只是结构，具体系数需用当前经济仿真决定。首轮不需要可自由输入的复杂票价；可采用“亲民 / 平衡 / 商业”少量赛季策略，提供清楚的收入与长期支持度取舍。

**防止强队滚雪球：** 需求以稳定基数为主，胜负影响小且有上下界；保留新人和弱队的基本观众。球迷不直接增加射门成功率、体力或所有属性。策略结算使用固定事件和稳定种子，不再额外加入一次大额随机抽奖。

**完整度验收：** 容量超过需求时确实出现空座；低价有增量观众但可能降低当场收入；支持度缓慢变化，不因一场失利断崖下跌。能够通过财务中心解释变化原因。

**旧存档：** 按当前球场和已有正式比赛初始化合理需求，保留容量、外观、合同；已购流星看台权益需单独迁移设计。首轮上线不应立即制造老玩家收入断崖。

### C. 商业合同——提高可控性和选择价值

保留普通/冠名等既有类别，将“等随机报价”逐步扩展为有限、公开的商业选择：

| 可选合同方向 | 玩家获得 | 玩家承担 | 与战术/经济的边界 |
| --- | --- | --- | --- |
| 稳定型 | 较低但稳定的赛季固定收入 | 较少上行收益 | 不绑定必须胜利，不压低弱队基本收入 |
| 经营型 | 观众/经营目标达成后的奖金 | 前期投入或票务取舍 | 用可验证的上座/运营目标，避免自动刷钱 |
| 品牌型 | 冠名较高收入及视觉展示 | 占用名额、名称使用期限 | 名称复原与历史记录一致 |
| 成绩型（后续） | 有上限的赛事奖金 | 有限履约风险 | 不成为所有强队唯一最优选择；不惩罚离线玩家 |

**最小补齐项：** 报价有效期、明确开始/到期赛季、续约窗口、已收/未收金额、到期通知与历史。每次发放和到期都使用稳定业务 ID。

**迁移原则：** 当前已签约合同仍按原一次性奖金和期限兑现；新合同规则按版本生效。不要重新发旧奖金，也不要把已收款误当成每季还要支付。

### D. 设施与建设项目——少量、有限、有机会成本

先完善球场项目，不立即加入完整建筑树：

- 每个项目显示总成本、预期改善、完成条件和资源占用；同一时间最多推进少量项目。
- 用比赛轮次或赛季事件推进，避免大量秒级定时器和反复写盘。
- 每条建设路线有终点或边际收益递减，满级之后仍有票务/合同选择。
- 只引入可解释的经营效果或工具价值，先不做永久全属性、伤病免疫、体力恢复等对比赛平衡有直接影响的增益。

后续可以考虑商业设施、公共战报分析工具或俱乐部展示建设。涉及隐藏战术信息的工具，要保持既有镜像市场的功能边界；不能因建设设施就免费泄露其他玩家完整方案。

### E. 赛季经营目标与俱乐部档案

让经营有短期结果和长期身份：

- 开季选择有限目标，例如稳定现金流、改善观众需求、完成一次建设、履约一份合同。
- 经营目标与足球成绩并列，弱队也能形成可完成的路线。
- 奖励以俱乐部装饰、展示或有上限的经营回报为主，避免再次增加无上限金币产出。
- 季末归档观众、收入、投资、合同和目标完成情况，与现有荣誉室并列而非替换奖杯历史。

该模块应建立在财务/球迷真实数据上；第一版不需要引入每日签到、重复任务或强制在线操作。

## 5. 建议分期

| 阶段 | 交付内容 | 规则变动程度 | 先决条件 |
| --- | --- | --- | --- |
| C1：看清现状 | 财务汇总、门票明细、合同时间线、扩容回收预测、经营季报 | 主要为只读派生与按需展示；保持已有经济 | 现有流水/比赛可对账，定义重置语义 |
| C2：形成取舍 | 球迷需求、少量票务策略、报价到期/续约、新合同版本 | 会改变收入分布，需独立验证 | C1 完成；旧看台/合同权益迁移；多日仿真 |
| C3：长期发展 | 有限建设项目、经营目标、长期俱乐部档案 | 新经营内容 | C2 证明有差异化选择且不存在唯一最优路线 |

**建议下一步先实施 C1。** 它能在不重写现有前台结构、不改变比赛结果的情况下补足经营反馈，并给 C2 提供真实数据。球迷和赞助的新规则不能伪装成等价性能优化。

## 6. 技术实施关键点

1. **先处理初始化清理。** `ensureClubManagement()` 当前明确 `delete supporters` / `delete attendance`。如果直接把新球迷状态写进同名字段，会在后续 view/初始化时被删除。需要显式 schema 版本迁移和一次性规范化，避免每次读取都修改新业务状态。
2. **从巨型服务中提取纯计算。** 财务聚合、需求计算、项目成本、合同结算分别独立；现有服务只负责权限、状态迁移、写账和返回。
3. **财务使用同一条账。** 不复制出第二份可写余额；历史季报是不可变快照，当前汇总带 revision，详情可追溯。
4. **以事件结算，不以页面访问结算。** 门票在赛事结算，期限在真实赛季切换，项目在规定事件推进；反复刷新不改变报价、需求、金币或进度。
5. **写入边界明确。** 同时改变余额、项目/合同状态、流水与通知的操作使用唯一业务 ID；重试、重启后继续不会重复扣费/付款。
6. **API 分层读取。** 俱乐部摘要留在原队伍视图，历史财务和合同明细按需请求；保存外观不应重算全部球员卡、市场和榜单。
7. **不扩散每帧工作。** 球迷、票务和经营不进入比赛每条控球链；比赛开始时冻结当场场地/经营必要快照。
8. **保持历史与新规则分开。** 以 `clubSchemaVersion` / `ticketRuleVersion` / 合同规则版本标记，旧收入、合同和冠名可回看且不重算。

## 7. 验证与平衡标准

| 目标 | 需要验证的场景 |
| --- | --- |
| 经济一致 | 签约、扩容、门票、奖励重复提交；赛季重置前后流水与余额核对 |
| 需求有效 | 相同球迷不同容量；相同容量不同策略；满座和空座场景 |
| 有经营选择 | 不同策略在收入、支持度、投资期限上有收益与代价，观察是否出现唯一最优路线 |
| 弱队可发展 | 排名下降不至于同时切断门票、赞助和目标收入；新人有可行的 C1/C2 路径 |
| 不主宰比赛 | 俱乐部设施不直接形成永久属性压制；收入对强化/X 成长速度的影响有上限和长期数据 |
| 跨季正确 | 正常每日换季、后台重赛/新赛季、完全重置分别符合定义 |
| 恢复正确 | 结算中途退出、重新载入、备份恢复和相同事件重放 |
| 性能保持 | 大流水、大历史、多人看同一比赛时，俱乐部页不触发全量历史扫描或整页重建 |

仿真至少覆盖多个日常赛季、不同排名、球场容量、金币余额和玩家活跃度。先报告金币净流入、投资回收、策略分布、培养速度和不确定性，再确定新规则参数；本报告不凭空指定最终票价或球迷增长率。
