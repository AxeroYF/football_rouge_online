# YFFM1 存储策略优化与服务器性能评估

日期：2026-11-04。目标配置：阿里云 2 核、2GB 内存、80GB 磁盘；用户反馈约 10 名注册玩家。服务器暂未续费，本次仅检查本地源码、修改本地存储实现，并在隔离存档上验证，未访问或清理线上数据。

## 结论

当前主要存储问题是旧文件被整目录保留，以及特殊备份没有过期策略。比赛的正常记录量不足以单独解释快速占满 80GB。保留分片结构即可先解决主要增长问题，现阶段没有必要为 10 名玩家立即重写成大型数据库服务。

本轮已修复文件回收、分段合并、备份保留和重复压实后的战报引用。JSON/NDJSON 格式与分片 schemaVersion=1 保持兼容，不要求重新迁移存档。比赛结果、球员资产、经济规则和前台显示逻辑未改变。

2GB 内存仍需控制峰值和后台任务并发。此次本地测试没有证明云服的容量上限，也没有证明所有接口的尾延迟已改善；下一阶段应处理同步序列化、较大的 core，以及战报按需加载。

## 正常比赛量与数据量

按目前正常 10 队完整赛程计算：

| 赛事 | 计算 | 每季场数 |
| --- | --- | ---: |
| 联赛 | 18 轮 × 每轮 5 场 | 90 |
| 冠军杯联赛阶段 | 9 轮 × 5 场 | 45 |
| 冠军杯淘汰阶段 | 4 组双回合 + 2 组双回合 + 单场决赛 | 13 |
| 赛季总决赛 | 胜者组 2 场 + 败者组 8 场 + 决赛 2 回合 | 12 |
| **合计** | 不含友谊赛、单次 AI 训练及历史批量任务 | **160** |

如果每天完整进行一季，则约 160 场正式比赛/天。不能再把这个数字乘以注册玩家数。杯赛未开启、赛事取消或赛程未完成时会更少。

使用真实球员池构建重特性/强化球队，以 V3.0 进行 5 场 180 链比赛，正式赛事当前设置为 `dotReplayEnabled:false`：

- 完整战报约 **110—129KiB/场**，平均 121.4KiB。
- 原样 gzip level 6 后约 **13—15KiB/场**，平均保留约 11.6% 的原字节数，内容可完整解压恢复。
- 160 场战报单份原文约 **18.97MiB/季**；压缩后约 **2.20MiB/季**。

这只是战报单份数据，不包含卡片、账本、直播检查点、赛季归档、备份和文件系统开销。赛季归档会重新包含完整战报，因此总磁盘量不能直接按 18.97MiB 作为每日全部增长量。当前归档数量上限为 12；特殊备份过去可能让更老的归档继续被引用。

另测一场开启圆点回放的样本，战报约 565KiB，其中回放约 437KiB。它说明历史回放数据可能更大，但**不是当前正式比赛默认开启回放导致膨胀**。

本地前台及球员头像相关目录合计约 37.4MiB，不含整个工程、发布包及日志。现有盾形 SVG 卡框属于静态共享资源，不是分片持续增长的主要来源。

## 已确认的增长机制与修复

| 问题 | 原行为 | 当前策略 |
| --- | --- | --- |
| 目录级保留 | 一个很小的账本分段或战报引用，就会保住所在 revision 的全部旧 core、卡库和索引 | 先遍历当前及备份的完整引用图，再回收未被引用的具体文件 |
| 分段数量 | 每次追加产生新的 NDJSON 分段，数量持续上升 | 达到 64 段后把当前完整记录合并成一个新段，不裁掉记录、不修改旧备份所引用的段 |
| 每日重置备份 | 只有纯日期备份受 7 天保留限制，`before-daily-reset-*` 永久留下 | 普通每日备份及每日重置前备份都保留最近 7 个日期 |
| 管理/迁移备份 | `before-*`、`pre-*` 没有到期规则 | 独立保留 30 天；使用操作时间或文件时间，不以旧赛季的数据时间冒充备份创建时间 |
| 重复压实 | 第一次压实把索引改为带数字前缀的文件名，后续遍历不能识别，清理可能删掉仍需的战报 | 统一识别原始及多次数字前缀索引；再次压实时继续遍历和重写嵌套引用 |
| 清理时长 | 没有按删除文件数限制单次工作 | 在线清理仍最多每 60 秒触发一次，每次最多删除 256 个文件，剩余工作后续继续 |
| 中断写入残留 | 临时 revision 缺乏安全的独立保留窗口 | 只回收超过 24 小时的未引用临时 revision，保留新建临时工作 |

恢复保护：

- 当前存档、所有尚在保留期内的备份引用，以及最近两个 revision 都受保护。
- 在删除任何文件前先校验完整引用图；遇到损坏备份、缺失文件、越界路径等异常时跳过清理。
- 当前引用不完整时，也暂停备份过期维护，保留旧恢复点。
- 清理计划执行前复核 manifest revision；离线工具仍要求停止对应服务，存档维持单写入者原则。
- 通过原子 manifest 提交和原有 fsync 流程维持写入可靠性，没有用取消落盘保障来换取速度。

`league.shardCleanup` 已加入现有运行指标，可区分清理耗时与总保存耗时。后台备份视图额外返回 `specialRetentionDays:30`，原有 7 天字段继续兼容。

## 本地对照结果

环境：Windows、Node.js 24.22.1、i7-14700KF。所有账号、联赛、内容与卡面工作室数据均隔离到临时目录；测试后删除临时目录，不操作真实存档。以下是合成存储样本，不能解释为线上已回收空间或真实云磁盘速度。

### 同一组 120 次资产操作

样本含 10 个 owner、每人 200 张简化卡记录、64KiB core；每次修改一张卡并追加账本与资产流水。最后执行引用回收直至该轮候选回收完成。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 当前真正引用的数据 | 422,551 字节 | 422,551 字节 |
| 实际文件逻辑占用 | 11.84MiB | 0.50MiB |
| 文件数量 | 503 | 137 |
| revision 目录数量 | 121 | 58 |
| 总文件量/当前引用数据 | 29.39 倍 | 1.25 倍 |
| 卡片与账本重载结果 | 正确 | 与输入完全一致 |

本样本占用减少 **95.75%**。剩余空间包括最近两个 revision 的恢复余量及 manifest。默认删除预算下，本样本需要两轮回收；不意味着上线后瞬间回收所有历史垃圾。

### 其他一致性与增长检查

- 连续 15 天：普通每日备份都是 7 份；重置前特殊备份从旧策略的 15 份收敛到 7 份。
- 45 天保留策略测试：每日两类各保留 7 个日期；过期管理/迁移备份被淘汰，保留的备份引用仍完整。
- 三次连续压实并清理：每次都可重载完整战报；旧缺陷已在修复前的临时目录中复现。
- 嵌入 12 份总决赛战报的 core，追加 12 次保存：文件量从约 19.28MiB 降到 2.97MiB；完整当前数据仍约 1.48MiB。core 仍大，尚需优化每次保存的 CPU/I/O 工作。
- 缺失引用、坏备份、越界引用、分段合并后恢复旧备份、删除预算、新旧临时目录均有专项覆盖。
- 队名及赛季名称即使包含类似文件路径的文字，也不会被回收或压实工具当成引用，更不会在压实时改写显示内容。

最终组合探针在父进程 `--max-old-space-size=512` 限制下完成。该参数限制的是 V8 堆，不是总 RSS，也不等于在 2GB 整机或阿里云上完成压力测试。

### 真实 HTTP 分片服务器测试

另外启动了使用真实 `LeagueShardStore` 的临时本机服务器，10 个注册账号中 9 队由玩家管理、1 队 AI。通过 HTTP 完成 20 次直接开包及 3 次三选一，实际获得 23 张卡；钱包未变化。停服回收后，完整资产和账本与回收前一致；再次启动服务后，卡片及钱包仍可恢复，缺失引用为 0。

服务进程同样限制 V8 堆为 512MiB；该短场景结束时 RSS 约 **142MiB**、heapUsed 约 **58MiB**。26 次保存的 p95 约 **24ms**，20 次直接开包 HTTP p95 约 **54ms**。场景没有同时运行整轮直播和大量客户端，不代表云端峰值承载能力。

## 整体性能判断

| 项目 | 当前判断 | 依据与下一步 |
| --- | --- | --- |
| 磁盘长期增长 | 本轮主要缺陷已修复，需上线后核验真实回收量 | 文件引用回收、保留期、分段合并已通过；历史文件很多时先使用停服离线回收 |
| CPU | 正常规模先保留 2 核测试，关注突发阻塞 | 当前直播每 100ms 最多推进一条链，而不是一口气模拟五场；仍与 API 共用主线程 |
| 内存 | 10 名玩家暂无本地证据要求立即扩容，但要留峰值余量 | 分片并不等于按需加载；当前赛季所有战报和卡片仍会进入内存 |
| 写盘与接口延迟 | 仍有后续优化空间 | 同步读文件比较、JSON.stringify、fsync、目录扫描及响应 gzipSync 仍在主线程相关路径 |
| 前端流畅度 | 与此次磁盘回收分开评估 | 已有 DOM 复用和静态缓存；大型卡库首屏与滚动仍需按实际设备测量 |
| 静态资源 | 不是当前主要空间矛盾 | 静态缓存为 16MiB；头像、框图可共享缓存，日后再按带宽需要接 CDN/OSS |

当前本机 V3 样本：单链推进 p50 约 13.4ms、p95 约 25.8ms；一场完整计算约 2.6 秒。五场样本在一进程内依次推进，仅测引擎工作，不包含 10 个真实客户端同时操作。此数值不能直接推算阿里云 2 核的响应时间。

单独冷进程加载 160 份当前战报（约 19MiB 引用数据），约 108ms；进程 RSS 从约 45.7MiB 到 78.4MiB，堆增加约 25MiB。这不是整个游戏服务器的内存；引擎、球员池、卡库、直播和 HTTP 缓冲还会增加占用。组合引擎样本在受限堆运行时，五场结束时父进程 RSS 约 284MiB。

本轮未证明写盘 p95 明显改善：资产样本仍为几十毫秒量级，较大 core 的样本更慢且波动较大。应把本轮收益归为存储占用收敛和恢复正确性，不能宣传成全游戏速度按 95% 提升。

Node 官方说明，同步文件操作、较重 JSON 处理与同步压缩会阻塞事件循环；把函数声明为 async 也不会自动把其中的 JSON.stringify 搬到其他线程。当前直播检查点虽异步写文件，其序列化仍值得后续测量。[Node.js 事件循环指南](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)

## 对 2 核 / 2GB / 80GB 的建议

1. **先保留现有配置，优先应用存储修复。** 开服后采集实际磁盘、RSS 和接口延迟，再决定是否加内存。避免仅因旧分片膨胀就扩盘，否则增长机制会继续消耗新增空间。
2. **一个游戏写入进程。** 不用多个 PM2/Node cluster 进程共享这套 JSON 存档。后台模拟并发应受控；已隐藏批量模拟前台，不代表历史后台队列自然停止。
3. **内存目标。** 初始以 Node RSS 约 0.8—1.0GiB 作为观察目标，给系统、Nginx、文件缓存及峰值留余量。持续超过约 1.2GiB、系统可用内存不足 250MiB 或发生 swap/OOM 时，再定位和调整；这些是建议告警线，不是强制杀进程配置。
4. **磁盘余量。** 建议总使用率 75% 告警、85% 紧急处理，尽量保留约 15—20GB 空间用于写入、恢复及运维。回收/压实需要的临时空间取决于有效数据量，不能把 80GB 全部当游戏存档预算。
5. **日志与发布包单独限额。** Nginx、systemd 日志启用轮转；服务器只保留少量可回滚发布包。它们没有纳入本次分片回收，重新开服时用 `du` 单独核实。
6. **云端备份。** ECS 快照保存在云端 OSS，按快照存储计费，可作为大操作前的恢复点；这和把完整备份包留在 80GB 文件系统中不同。[阿里云快照说明](https://www.alibabacloud.com/help/en/ecs/user-guide/snapshot-overview)
7. **长期应用备份可放 OSS。** 按日打包完整可恢复的引用集合及 manifest，校验上传成功并完成恢复测试后，再轮转本地旧副本。7—30 天短期备份优先评估标准存储，不盲目转归档；低频/归档涉及最短存储期、取回费和小对象请求成本。通过独立前缀设置生命周期，不能只上传一个依赖本地文件的 manifest。[OSS 生命周期说明](https://www.alibabacloud.com/help/en/oss/user-guide/overview-54/)

## P1 完成情况与后续顺序

2026-11-04 已完成下表四项 P1，格式兼容、恢复、真实总决赛和本地 HTTP 验证及前后对比见 [P1 存储优化记录](YFFM1-STORAGE-P1.md)。本文上面的数字保留为 P0 阶段基线。

| 优先级 | 建议 | 目的与边界 |
| --- | --- | --- |
| P1 | 将总决赛完整报告从频繁重写的 core 中拆出，或改为独立战报引用 | 降低每次交易/开包的序列化与写入量；需版本兼容及回滚验证 |
| P1 | 已完赛战报与赛季归档采用压缩存储，按详情访问解压并设有界缓存 | 本地战报压缩约节省 88% 字节；保持完整事件、战术复盘及前台内容 |
| P1 | 保存只序列化一次；细化到 owner/具体分片的脏标记 | 减少重复计算和未变化分片的同步读取比较，不取消必要持久化 |
| P1 | 当前赛季历史战报按需读，避免启动全部解析 | 降低大存档常驻内存；当前 archive 已是摘要加载，可沿用这个方向 |
| P2 | 已开礼包、已回收卡片和结束交易迁入审计归档，热数据保留必要 ID/幂等标记 | 界面过滤不等于底层记录已消失；迁移前须保护奖励、防重和交易引用 |
| P2 | 高峰数据证明需要后，再评估单个计算 Worker 或数据库 | 先控制内存和单写入者；不为 10 名玩家直接引入多进程并发写入 |

四项 P1 已在后续本地实现，P2 尚未实施。完整战报和原比赛结果继续保留；旧未压缩文件受备份引用保护，直到保留期到期并完成回收才释放空间。

## 检查、工具和重新开服步骤

本地相关回归累计 **159 项通过**，覆盖分片、存储策略、压实、资产、免费装饰、卡包市场和真实 HTTP 注册/登录，另完成上述 10 账号 HTTP 分片及重启场景。HTTP 测试首次因执行环境禁止本机网络连接而失败，允许隔离本机连接后通过。源码语法检查 303/303 通过；未把存在历史问题的完整长跑套件算作通过。

源码入口：

- `versus/infrastructure/shard-references.js`：完整引用图、文件回收计划和执行。
- `versus/league-shard-store.js`：分段合并、限频及限量回收。
- `versus/league-service.js`：备份保留期和当前引用完整性保护。
- `devtool/compact-league-shards.js`：重复压实修复及离线回收。
- `scripts/audit-league-storage.mjs`：只读空间审计，统计当前引用、备份独占、受保护目录内无引用文件、最新两版余量、临时目录和实际文件字节。

默认配置：

```dotenv
YDL_SHARD_CLEANUP_INTERVAL_MS=60000
YDL_SHARD_GC_MAX_FILES=256
YDL_SHARD_MAX_LOG_SEGMENTS=64
```

本地输出在 `outputs/storage-assessment/`：`before.json`、`report.json`、`synthetic-storage-audit.json`、`comparison.json`，真实 HTTP 场景为 `sharded-http.json`。它们包含隔离样本及本机环境，不是线上数据报告。测试日志在 `outputs/tests/`。

服务器恢复后：先确认实际数据目录、备份目录、有效引擎环境变量及运行版本；创建可恢复快照，停服取一致副本，在副本上只读审计并恢复验证；应用新代码，确认资产/钱包/比赛历史正确，再对已验证目录执行离线回收 dry-run 和 apply。线上根目录未确定前，不按日期或 revision 数字直接删除目录。

只读审计命令（把路径换成实际分片目录）：

```sh
node scripts/audit-league-storage.mjs /actual/path/to/league-shards
```

另行收集 `df -h`、`df -i`、数据目录 `du`、`free -m`，以及现有受令牌保护的 `/api/diagnostics/metrics` 中 RSS、`league.save`、`league.shardCleanup`、`league.liveSlice`、事件循环延迟。临时目录和未知/损坏引用必须先排查；审计数字本身不是可直接删除文件的指令。

本次未提交、推送、部署，也没有修改真实玩家存档。
