# V4 原存储结算桥

`canonical-storage-settlement.js` 使用原联赛服务的 JSON 或分片写入器，把业务状态和 V4 回执放在同一次提交中。当前只允许带 `v4-local-storage.json` 标记的本地副本，服务路径必须位于该目录内，自动备份关闭。没有正式服务配置开关，也不改变真实存档。

## 提交与恢复

完整战报先经过版本、输入指纹、球队、个人统计和事件校验。首次处理时持久化输入、赛季、结果摘要、赛事上下文和结算时间；业务变更使用这份锁定信息，并沿用原联赛或杯赛消费函数。消费后核对累计统计和唯一比赛记录。

下一次原存储提交同时写入业务结果与 `v4LocalSettlements.receipts`。JSON 使用原文件原子替换；分片使用原清单切换，回执属于核心状态分片。重启后先查回执，因此不会在“业务已提交、调度尚未确认”的窗口重复发放或累计。

写入报错后先重新读取磁盘：若对应回执已提交，返回已提交结果；若磁盘仍为原状态，恢复内存并报告失败。Windows 的短暂权限/共享冲突只在确认磁盘未变后做有限重试。不能判断提交状态时停止该次结算。

存储桥拒绝检测到的内存与磁盘差异，避免用旧内存覆盖已保存的修改。此检查要求所有写入由同一宿主负责；它不把不遵守锁协议的其他旧进程变成可并发写入者。导入副本后应通过正常加载流程重开服务：分片存储把历史归档正文保存在冷文件中，内存只持有摘要。正文保持原样，不能通过忽略整个归档字段绕过一致性校验。

分页收件箱只影响原服务的页面返回格式，不改变完整的存储状态，已纳入验证。原业务生成新增流水 ID 时仍使用实际时钟；独立副本之间这些技术 ID 可以不同。资金、业务时间和随机序列按锁定信息核对，已提交流水 ID 在重试和重启后保持不变。

## 录像中断写入

实际杀进程测试发现，未提交的清单或分块可能只写出一部分。锁定内核重演时，仅允许补齐与预期字节严格一致的前缀；不覆盖冲突内容，也不修补已经提交的损坏分块。分块与待提交清单同步落盘后，才发布清单。已有帧、事件、权限和压缩协议不变。

受限压力复测又捕获了 Windows 清单共享冲突。清单替换的等待重试上限调整为32次（总等待约2.9秒），其他调用仍保留原上限；不可重试错误直接报错。读取端最多保留一个正在执行和一个待执行的清单读取，只有尚未开始的读取才可由多个请求共享，确保提交后发起的刷新不会得到提交前的快照。

## 验证与剩余工作

- `test/engine-v4-canonical-storage.test.js`：JSON/分片各验证调度接入、并发幂等、过期内存拒绝、写入前失败、写入后异常、提交前后实际杀进程及重启；覆盖分页模式。
- `scripts/verify-v4-canonical-storage-local.mjs`：复用八场已验收完整战报，分别在真实存档的 JSON 和分片副本中核对比赛、积分、球员统计、钱包/资产、收件箱、预测结果与历史归档正文，再重启核对回执。
- 录像写盘变更另由归档前缀恢复、生产中杀进程、浏览器与受限生产/观看容量验证覆盖。

当前验证的是正确性和恢复能力。存储桥仍有同步全状态核对及提交，未证明与实际业务 HTTP 并发时满足延迟预算。正式赛程入口、跨轮次重新准备、赛事重叠约束、最终宿主容量和云主机验证仍待完成；用户已要求暂不连接云主机。

受限容量的八场/120秒尝试只完成六场，证据保留在 `outputs/v4-stream-capacity-20261118/iteration15/capacity.json`。单场耗时与此前四场测试基本相同，主要是四批队列所需时间；不能把该失败解释成120秒通过，也没有修改正式比赛时长。

共享冲突修复后的 `iteration17/capacity.json` 通过180秒预算：两个逻辑核/2GiB、两名生产者、八场完整真实阵容比赛与十名观看者，八场全部完成，无生产者失败、429或服务端过载；head/segment P95为70.11/98.66ms，峰值RSS约264MiB。更早180秒运行的共享冲突失败保留于 `iteration16`。该测试仍不包含资产/预测并发请求，也不证明实际云主机性能。
