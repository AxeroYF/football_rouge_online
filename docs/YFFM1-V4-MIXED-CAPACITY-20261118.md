# V4 本地混合业务验证

本阶段验证整轮 V4 比赛与原业务并行工作，继续只操作隔离副本，正式服务不启用。

## 修复

原收件箱已读接口会先修改内存，再延迟保存。原存储桥此前把这段合法的延迟写入视为存储冲突，导致逐场结算中止。

现在仅当原延迟保存标记仍存在，并且逐字段核对证明差异只有既有消息单调增加的 `readAt` 及 `updatedAt` 时，先调用原同步保存，再完整核对一次。钱包、阵容、消息内容、外部磁盘变更仍拒绝覆盖。保存前后抛错都会保留可恢复的状态；不会把任意未保存变更混入比赛事务。

独立循环负载的 iteration5 暴露了清单重复解析开销。归档读取现在每次仍读取磁盘，只在完整字节与上次已验证的清单相同时复用验证结果；变化后仍检查全部历史和追加游标。测试覆盖同大小篡改、失败后恢复以及新分块追加，不以文件大小或时间戳代替内容核对。

## 验证范围

- 两种原存储各覆盖已读协调、非法变更拒绝、保存前后失败重试。
- 使用 48 号冻结的 16 场完整比赛，在当前 JSON/分片桥各重放两轮，对比比赛、个人数据、积分、钱包、卡包、预测和收件箱。原奖励流水 ID 包含墙钟时间，因此只对新流水及其收件箱引用做经过逐条内容验证的一一映射；重开后的实际 ID 必须完全不变。
- 十个通过原选秀及账户流程建立的隔离账号，调用原联赛 HTTP API、分片存储和动态鉴权回放。整轮八场生产/结算同时运行，期间读取联赛、预测、收件箱并标记已读，另启动一次原 V1/24 样本后台预测并检查实际发布。
- Windows Job 限制服务、比赛生产子进程和预测 worker 合计两个逻辑处理器、2 GiB 内存；请求客户端在 Job 外。本机回环，不代表香港云盘或网络性能。

早期 iteration2 暴露了上述已读冲突，失败证据保留。iteration3/4 是每个客户端依次请求画面和业务的负载。iteration5 改成每个账号独立运行观看与业务循环，两个循环各等待 300 ms，head P95 为 152.15 ms，超出门槛，未通过。iteration6 在相同模型下验证清单优化，验收以该模型为准。

门槛为 180 秒内完整结算八场、十账号参与、八场首画面均在 10 秒内出现、预测实际发布 24 样本、无业务/生产错误、Job 峰值小于 1.5 GiB，head/业务 P95 小于 150 ms、分块 P95 小于 300 ms。报告同时记录最大延迟，不以 P95 掩盖结算时同步操作造成的峰值。

## 边界

轮次结算仍有同步核对、克隆和整状态写入；目前尚未消除约一秒的响应峰值。分块负载每个观看周期只读一个分块，64 倍公开时钟用于在预算内完成发布，并非验证所有客户端持续以 64 倍完整追赶录像。

未接入生产定时器、杯赛/赛季决赛整赛事流程或录像保留策略。未连接云主机，未改原预测样本数和赔率。旧引擎及真实存档通过既有保护核对；`league-service.js` 仅保留此前已审查的三处 V4 点球受益统计兼容表达式。

验证入口：`benchmark-v4-mixed-local.mjs`、`verify-v4-round-replay-local.mjs`。验收结果和实际数字以新的独立源码冻结报告为准。
