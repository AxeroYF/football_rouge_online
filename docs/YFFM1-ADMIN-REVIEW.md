# YFFM1 管理员后台审阅

日期：2026-11-12。范围：后台前端、管理员 API、联赛管理操作、球员/特性覆盖、卡画与批量制卡、相关测试。采用源码检查和隔离数据探针；未修改运行代码或真实玩家存档，未操作真实管理后台。

后续实施：本报告列出的 P1 已修复，赛季重置已按“只有完全重置影响金币”统一；详见 [落地规则与验证](YFFM1-ADMIN-P1-AND-RESETS.md)。下文保留审阅时的发现及原始证据，P2/P3 仍作为后续优化建议。

## 总体判断

功能已经覆盖日常运营，暂不需要推倒重写。应先处理比赛推进和数据写入的一致性，再拆分重型页面和响应，最后统一界面与清理历史代码。

当前后端主要复用联赛领域方法，避免另建一套发奖/结算规则，这是合理基础。后台仍混合了旧快速比赛的统计口径与 YFFM1 的经营管理口径，部分界面承诺与实际规则不一致。

## 优先处理的发现

### P1：直播轮次中手动模拟会重复结算已完成的比赛

`simulateNextRound()` 只排除报名期、已结束赛季和已完成轮次；轮次为 running 时仍会遍历全部 fixtures。`simulateFixture()` 没有跳过已经完成的 fixture，也没有复用正在进行的直播比赛。

隔离测试先按实际引擎完成并结算同轮 1 场，再执行手动模拟：一支球队的已赛场次从 1 增至 2，当前轮次保存 6 条比赛记录，但只有 5 个不同比赛 ID。重复结算还会经过球员表现和伤停等处理，不能只在展示层去重。

建议：服务端拒绝正在直播或等待结算的轮次再次创建模拟；若需要“立即结束当前轮”，应推进已有 match 对象，通过原结算队列收尾。最终结算也应按 fixture ID 保证只执行一次。前端据赛季/轮次状态禁用按钮。

定位：`versus/league-service.js:10328`、`:9456`、`:9405`；`versus/admin-api.js:346`。前台按钮“立即模拟下一轮”始终可用。

### P1：内容保存校验失败，仍可改变运行中的数据

`applyPlayerPatch()` 和 `applyTraitPatch()` 直接按字段顺序修改全局对象，再验证后续字段。后续字段抛错时，前面的修改没有回滚，也不会正常进入持久化流程。

隔离复现：

- 向门将提交新姓名、主位置 ST、副位置 ST，返回“副位置无效”，但姓名、主位置和球员池已变为新值、ST、ATT。
- 修改特性名并提交非数组规则，返回“特性效果规则必须是JSON数组”，但运行时特性名已经变化。

这不是单纯的错误提示问题：界面报告失败，进程仍可能使用未保存的修改，重启后又恢复另一份状态。正常表单中修改主位置而保留相同副位置，也可能触发这类跨字段冲突。

建议：在副本上完整规范化并校验；全部通过后再同步球员对象、位置池索引、覆盖数据和持久化。卡画替换也应采用“先校验、临时文件、成功提交”的顺序，避免先覆盖图片再发现定位参数无效。

定位：`versus/ydl-content-store.js:80`、`:126`、`:340`、`:368`；`versus/player-card-studio-store.js:388`。

### P1：赛季重启/换季的金币提示与实际行为冲突

后台顶部及确认框称“重启与新赛季都会保留……金币”。实际 `resetCompetition()` 会将真人球队余额设为初始本金，并清空本赛季 ledger 等记录。

隔离复现：余额 12,345，执行重启后变为 100,000。

需要先明确产品规则：若每赛季应重置本金，就应在按钮、影响预览和确认框中明确说明；若重启仅重置比赛，就应分离重启和换季的资金策略。不能直接把本次审阅理解为要求后端改成保留金币。

定位：`admin/public/app.js:248`、`:446`、`:449`；`versus/league-service.js:11635`、`:11646`。

### P2：金币等发放缺少请求幂等与提交锁

通用 `runLeagueAdminAction()` 没有 pending 锁，金币表单提交也不禁用按钮；发放方法每次创建新 grant，不识别请求幂等键。

隔离 API 连续提交两次相同 requestId 的 1,234 金币请求，最终到账 2,468，产生 2 条发放记录。两次独立发放当然可以合法重复，但同一次操作的双击、网络重试不应变成两次发放。

建议：前端提交锁；服务端 requestId + 参数摘要 + 结果回执；同一请求返回首次结果。推广至礼包、点数、单卡和全服通知，保留各自领域逻辑。

定位：`admin/public/app.js:302`、`:474`；`versus/league-service.js:2753`。现有玩家强化/洗点已有 requestId 模式，可借用实现思路。

### P2：运营总览没有覆盖 YFFM1 的正式赛事

`uniqueMatches()` 只遍历 `versusRooms.accounts[*].matches`。联赛、杯赛等记录在联赛服务的 `state.matches` 与归档中，没有接入这份统计；玩家胜负与进球摘要也沿用快速房间的账号生涯数据。

隔离数据有 6 条联赛记录时，总览仍显示比赛数 0。该样本包含上述重复结算探针产生的记录，但“未接入联赛数据源”的结论不依赖重复记录。

建议：总览明确区分快速比赛、联赛、杯赛和总决赛；默认显示 YFFM1 正式赛事。竞技统计增加引擎版本和战术模型筛选，新原则分别统计，避免仅以旧 style 字段概括球队打法。按比赛元数据汇总，详情按需读取。

定位：`versus/admin-api.js:79`、`:123`；`admin/public/app.js:118`。

### P2：晚到请求能覆盖当前管理页面，缓存也缺少联动失效

内容分区加载完成时只判断 section 是否仍等于内容选项卡，没有检查管理员是否已经切到“运营总览”或“联赛”。用源码中的真实 `loadContentSection()` 做隔离函数测试：请求发出后切到总览，晚到响应会把页面重新渲染成内容页。

球员保存只更新 players 缓存；已加载的卡画目录、分析和概况不会联动失效。其余内容操作也需建立相同的依赖规则，否则跨模块看到的姓名、评级和数量可能不同，直到手动刷新。

建议：统一 activeView + 页面请求序号/AbortController；退出、切页时丢弃旧响应。按实体 revision 或明确依赖失效缓存。请求超时、401 和普通错误使用一致处理。

定位：`admin/public/app.js:618`、`:1257`、`:1269`、`:1347`。

### P2：登录限流无条件信任转发头

`clientKey()` 优先使用 `cf-connecting-ip`、`x-forwarded-for`，没有在应用内限定可信代理。

隔离 API 测试：同一 socket/转发头连续失败后返回 429，只修改转发头即恢复为 401。若上游完整重写并清理这些头，风险可由上游控制；否则这不能视为可靠的按来源限流。

建议：直连使用 socket 地址，仅在配置的可信代理后解析转发头，并清理过期失败计数。保留现有随机会话、密码比较、服务端鉴权与生产强密码要求。

定位：`versus/admin-api.js:38`、`:200`；`src/runtime-config.js:17`。

## 性能优化：哪些已经做了，哪些还值得做

已落实的优化应保留：

- 内容按 summary/players/studio/analytics/traits 分区加载，制卡列表不重复携带 26 项属性。
- adminView 通过一次卡片扫描建立 allocations 索引；经济流水一次按玩家分组，并建立交易索引。
- 指定球员卡发放已有紧凑回执，不能将所有管理操作笼统视为返回完整联赛。
- 卡画使用二进制与 WebP，批量上传限制并发，Excel 先预览再提交。

本次桌面隔离样本：

| 数据 | 构建视图 | JSON 序列化 | gzip | 原始 JSON | gzip 后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单真人球队小样本 | 2.0ms | 0.5ms | 2.1ms | 167,891 B | 25,277 B |
| 同一球队构造 20,000 条流水 | 24.1ms | 25.4ms | 29.2ms | 8,001,379 B | 389,310 B |

这不是线上服务器容量测试。它说明旧的多秒卡片扫描问题已不是同一瓶颈，但完整流水在 ledger、transfers 等数组重复输出，JSON 与同步压缩成本仍随数据增长。小操作也不需要重算并返回全部球队经济明细、完整球员目录和所有发放历史。

另外，实际五场同步手动模拟在该隔离样本耗时约 9.3 秒。该计算运行于主线程；即使比赛状态冲突修好，也应改为任务提交/进度回执，分步推进已有比赛，而不是在一个管理请求中同步跑完。

内容侧 `summary` 仍调用完整 `playerCardStudioView()`；后者按每个批次重复过滤全部草稿及已发布球员。`updateYdlPlayer()`/`updateYdlTrait()` 为返回单个实体又构建完整 `ydlContentView()`。可分别改为计数摘要、一次批次分组及单实体序列化。

## 可清理但不应优先于正确性的内容

- `DEFAULT_ADMIN_PACK_TYPES` 仅定义未使用；教练工作室整段处于注释中，属于未启用代码，不是当前暴露了坏入口。
- FT1/S4/YDL/YFFM1 文案混用；统一显示名称即可，内部兼容标识不要盲目批量替换。
- 旧冲突恢复分支依赖 `YDL_SEASON_DATA_CONFLICT`，当前联赛服务没有该错误生产点，API catch 也未转发 code。应确认是否仍需支持旧迁移，再删除失效入口/测试或恢复完整契约，不能把当前普通故障都引导到清空赛季。
- 前端约 1,479 行集中管理三大页面，API 约 474 行串联路由。适合按总览、赛季、发放、纪律、内容工作室拆模块，共用请求层和表单组件；拆文件本身不会解决业务问题。
- 三人并发上传等已经有效的机制不要重复重写；存量奖励包及老数据兼容逻辑在确认引用前不能因名字旧而直接删除。

## 建议实施顺序与验收

1. **正确性修复**：已结算 fixture 不再执行第二次；失败保存对运行数据及磁盘零影响；赛季资金行为与确认文案一致。
2. **写操作可靠性**：同 requestId 重试不多发资产；按钮防重；已有正常独立操作仍可重复执行。
3. **统计与响应拆分**：总览覆盖正式赛事；联赛首页只读概况，经济、流水、目录按需分页；同步模拟改任务调度。
4. **前端状态和缓存**：晚到响应不覆盖当前页面；修改内容后相关模块自动更新。
5. **结构与视觉清理**：拆模块、归档死代码、统一名称及卡面组件。

现有相关测试 7 文件、10 项通过；它们主要覆盖正常鉴权、内容分区、制卡上传/发布等路径，没有覆盖本次复现的直播中重复结算、失败写入及重复发放场景。修复时应新增这些行为回归，不能只调整源码正则断言。

证据：`outputs/admin-review/probe.json`；可复跑隔离探针 `node outputs/admin-review/probe.mjs`。它创建独立 fixture 目录并模拟管理操作，不启动真实服务器，不读取真实账号或修改真实存档。相关测试报告：`outputs/tests/2026-11-12T02-01-48-517Z/report.json`。
