# YFFM1 功能系统完整度与优化评估

评估日期：2026-11-04（北京时间）。对象：本地 `D:\Yangfan\YFFM\YFFM1` 当前工作区，包含已经实施、尚未提交的前端性能优化和 V3.0 引擎变更。本报告不代表 GitHub 默认分支或线上服务器的实际发布状态。

范围修订：用户已明确世界杯与主教练为永久废弃功能，今后不再使用。以下保留其残留代码的核验事实，但不再把这两项视作需要补齐的玩法，也不因其不可用降低活跃功能完整度。俱乐部深化评估另见 `docs/YFFM1-CLUB-ASSESSMENT.md`；卡框复用来源为同仓库 `codex/rougelite`，不是 YFFM3。

## 1. 整体判断

**YFFM1 已有较丰富的足球经营主循环，当前最需要的是把这些系统稳定地连接起来，并建立可信的性能、结算和回归基线。**

建队、阵容战术、联赛/杯赛/总决赛、球员资产、强化、X 成长、交易、俱乐部和观赛均有实际实现。主要短板集中在四个方面：

1. **废弃功能与活跃功能的代码边界仍需整理。** 世界杯、主教练已确认永久废弃，不再补齐；这些残留与已下架的大名单扩容仍有旧接口、旧代码或旧测试，属于清理工作。
2. **功能数量领先于验证能力。** 本次完整测试 68 个文件，64 个通过、3 个失败、1 个超时；超时文件在结束前已出现 15 项失败。部分是旧规则/旧版本夹具，另一些仍需排查。
3. **V3 与其他系统的联动尚未充分验证。** 比赛波动已下降，但预测仍使用 V1 定价，培养、奖励、镜像市场和赛季经济还缺少同一版本下的长期联合验证。
4. **流畅度改善已落地，但后端和大存档仍有优化空间。** 重复 DOM 重建已减少；完整联赛视图、资产派生计算、历史数据处理、持久化与集中结算应成为下一轮排查对象。

不能仅凭页面、接口或某个测试文件通过，给项目一个“完成度 90%”之类的数字。更有用的判断是：**核心玩法已有闭环；跨系统稳定性、规模化性能和多端交付尚未完成验收。**

### 评估范围

- 主体游戏：`server.mjs` → `devtool/server.js` → `versus/api.js` / `versus/league-service.js` / `versus/public/app.js`。
- 后台：`versus/admin-api.js`、`admin/public/`，以及内容和卡牌工作室服务。
- 辅助模式：旧好友房间、AI 训练、镜像与算力节点、Windows/macOS 离线版、Android TV 客户端。
- 根目录同名 `app.js`、`league-service.js` 等归档副本、`game/` 七人制原型，不作为主体联赛的功能实现证据。Rougelite 是另一条分支产品，也不计入本报告。

| 标记 | 含义 |

## 3. 各功能系统详细评估

### 01. 账号、身份与登录

**已有能力：** 昵称注册、密码登录、旧设备身份升级、个人资料、修改密码、账号处罚和登录暂停。密码使用加盐 scrypt；账号存档采用原子替换和失败处理。基础认证不是占位代码。

**本次核验：** 注册、登录、改密成功；改密后旧 `accountToken` 仍能读取联赛，重新登录也返回同一凭证。代码中玩家注册只要求密码非空，而改密要求至少 6 位。管理员已有失败次数限制和会话时效，玩家登录路径未见对应的服务内限流。

**判断与优化：** 基础流程闭环，会话生命周期不完整。优先建立凭证撤销/轮换策略、统一密码校验；将玩家登录计算移出高频游戏推进的阻塞风险范围，并核验代理层是否另有限流。注册/登录中的同步 scrypt 是排查事件循环延迟的候选点，尚未据此测出并发容量。会话和密码策略属于行为调整，应与等价性能优化分开实施。

### 02. 新手建队与选秀

**已有能力：** 在 10 个联赛席位中接管 AI，按位置池进行 22 次三选一，继续选择 X 球员、主副位置、身高及初始特性，完成注册。已有球员占用、席位占用、重名和提交时再次校验；中途可恢复选秀状态。开发模式另有自动选秀。

**本次核验：** 使用公开模式正常手动完成 22 人选秀和 X 配置，最终名单 23 人；没有借用开发自动选秀跳过主要流程。公开模式自动选秀返回 404，符合限制。

**优化：** 核验长时间放置的草稿对席位和 X 选择的占用策略；覆盖断线后重新进入、两个设备同时选人和最后一步网络重试。当前选秀允许自由位置构成；若增加位置引导，应保持为明确的产品设计项，不能在性能修改中悄悄加入强制限制。

### 03. 阵容与名单管理

**已有能力：** 首发/替补、站位、队长、体力红线、名单容量、特殊球员和超限锁定；选卡、强化、所有权及交易会影响实际可用名单。

**缺口：** 当前已恢复 33 人名单规则，付费扩容已下架；旧扩容测试仍按旧规则运行。完整联赛测试还出现自动轮换后的站位断言失败，夹具直接使用旧推进函数，需要区分版本适配与真实继承问题。

**优化：** 把“能注册、能出场、能交易、能作材料”四种资格分别集中校验。使用同一名单规则服务生成前端提示和后端校验；对轮换后不同比赛阶段的职责、站位和队长设置增加跨版本回归。验收应包括“阵容方案原样保存并被比赛正确采用”，不能只验收保存接口返回成功。

### 04. 战术板、方案与分享

**已有能力：** 默认/领先/落后方案、比赛阶段、持球/无球职责、八项连续战术维度、进攻防守方向、拖动分线、阵容方案切换与复制、赛事分配、分享导入导出和动态形态预览。已加入方案 ID/revision 校验，减少旧请求覆盖新方案。

**现状：** 前台操作空间已经相当丰富，主要问题是这些控件是否在比赛中产生稳定、可解释的区别。当前 `timeWasting` 仍不是通过减少实际控球链数量来消耗比赛时间，其效果不能直接理解成少给对手若干次进攻。

主联赛主要依靠赛前保存方案及比分阶段自动切换。旧好友房间的战术暂停/现场调整有独立路由，不能直接算作主联赛已经拥有同等的实时指挥功能。

**优化：** 为“编辑值 → 保存值 → 比赛采用值 → 预览值”建立一致性检查；缓存只依赖当前方案/球员状态的派生结果，正确失效；把冲突错误和保存状态稳定反馈给玩家。分享导入已带版本保护，但长跑测试仍有旧调用方式未跟上。保留现有控件和显示逻辑，优先减少重复读取表单、重复投影和相同节点更新。

### 05. V3.0 比赛引擎

**当前版本：** 新联赛、杯赛和友谊赛默认 `engineVersion:3.0.0`、`engineProfile:v3.0-tactical-control.1`；AI 训练和镜像批量也使用 V3。共享计算仍放在 `versus/v2/`，内部数据格式 `version:2` 不表示实际引擎仍是 V2。旧房间和历史比赛另有边界。

**已形成的能力：** 控球链、空间覆盖、连接、职责、动态站位、比分阶段、球员能力、体力、天气裁判和特殊事件。V3 加强空间和应对的作用，降低执行能力差的直接权重，并引入混合分组抽样。

**证据与限制：** 前轮同实力配对样本中，净胜球标准差从约 1.566 降到 1.176；方向/防守覆盖实验观察到对手相关差异。这支持优化方向，但不等于已经证明全阵型克制平衡，或战术必能抵消某个固定能力差。真实名宿、高强化、X、复杂特性和长期赛季仍需联合验证。完整套件中的旧 V2 红牌与动态快照用例尚有失败，不能直接推断为 V3 同一缺陷。

**优化：** 在真实阵容上按阵型、职责、战术、能力差、天气做交换主客和共同种子的配对实验；同时看胜率、净 xG、射门质量和异常事件占比。为每项战术建立“有收益的场景、付出的代价、对手应对方式”。具体实验和边界见既有 `YFFM1-V3.md`。

### 06. 联赛、日程与自动推进

**已有能力：** 10 队赛程、积分和榜单、定时比赛、真人接管 AI、每日重置、赛季结算、后台模拟与重启。正式推进与直播小切片已经分开调度。

**缺口：** 自动任务依赖联赛、杯赛、总决赛完成状态；复杂分支集中在一个服务中。长跑测试中赛程启动数量、赛季状态及奖励预期存在失败。本次没有完整模拟“连续多个自然日、重启、补算与全部奖励到账”的线上等价运行。

**优化：** 将日程和结算视为可恢复的状态机；对跨日、迟启动、停机后恢复、延期比赛和手动操作组合建立场景表。按日期、赛事、轮次、结算 ID 记录进度，明确任务是否已启动/已完成/已入账。保持现有开赛时间和展示规则，先消除重复扫描和无变化写盘。

### 07. 杯赛

**已有能力：** 10 队、9 轮单循环联赛阶段，排名后进入八强；八强和半决赛两回合、决赛单场。包含种子/平局处理、晋级、转播、奖励和赛事伤停逻辑。

**完整度判断：** 结构完整，不能因为另有世界杯残留就否定杯赛；两者是不同系统。风险集中在淘汰赛结果与奖励、伤停的联动。

**优化：** 覆盖两回合总比分相同、次回合点球、延期和重启；同一淘汰结果重复恢复后只晋级、发奖一次。赛程与对阵视图可以按杯赛 revision 复用，避免所有玩家刷新时重新生成未变化的结构。

### 08. 赛季总决赛

**已有能力：** 联赛/杯赛成绩综合种子、冻结快照、分支对阵、Ban 选择、同时开赛波次、决赛路径和冠军星。已有较专门的状态、跨日取消、时间锚点和重载测试，本次相关测试文件通过。

**本次核验：** 玩家总决赛查询接口可用；这只验证读取，不代表已经人工玩完 Ban 和全部赛程。

**优化：** 优先验证联赛/杯赛最后一场延期时种子冻结的一致性，Ban 截止前后的竞态、决赛体力处理及奖品发放。与每日结算的前置条件显式连接，避免某一赛事取消/未完成让其他奖励无提示地一直等待。

### 09. 直播与电视台

**已有能力：** 正在直播、比赛预告、观赛加入/退出、比分、站位、赛况、统计和赛后收尾；覆盖多种赛事。旧房间还使用独立流式快照路径。

### 31. 运营后台与内容工具

**已有能力：** 管理员登录和会话、玩家/赛事查询，模拟、每日重置、赛季恢复，金币/卡/礼包/X 点数发放，纪律和邮件，球员/特性配置、卡牌工作室、Excel 模板/预览/导入、图片处理与批次发布。危险赛季操作已有明确确认字符串；生产密码限制和账号去敏也已实现。

**缺口：** 同一服务承载内容变更、资产发放和赛季状态管理，影响范围较大。隔离空内容测试中的管理员用例，仍假设布冯固定为 90，暴露测试依赖运营覆盖数据；本次没有人工点击验收后台全部入口。

**优化：** 把“预览差异 → 校验 → 应用 → 结果/审计”统一为批次流程；发布内容后统一失效相关缓存，并检查正在进行的比赛是否使用冻结快照。对发放/回滚建立可查业务 ID。部署策略、审计保留和账号权限扩展需根据真实运营规模确定，不能仅按工具数量判断后台成熟度。

### 32. 存档、备份与恢复

**已有能力：** 账号原子写入/失败保护、联赛 JSON 或分片、manifest 和 revision、备份保留、赛事归档、直播检查点、队列写入和结算任务。本次账号、队列、分片安全/压缩等相关测试通过。

**限制：** 单文件原子替换不自动保证账号、联赛、内容和所有分片之间是一个完整事务；现有服务也不能据此直接多进程并发写同一存档。长跑中“备份与全重置”组合用例在 tick 状态断言处失败，尚不能据此宣称备份文件已损坏。

**优化：** 做可重复的故障演练：写入前/中/后退出、损坏目标文件、manifest 指向缺失分片、结算入队后重启、备份恢复后重跑任务。验收不只看 JSON 能解析，还要对账金币、资产、赛事与任务状态。迁移到数据库应由实际写入量和运维需求决定；先把当前单实例模式的正确性与恢复能力验证完整。

### 33. 流畅度、请求与后端运行

**已有改善：** 同页模板增量更新、稳定节点复用、强化选卡局部刷新、直播避免双重布局、重复请求合并、隐藏轮询暂停、静态缓存/ETag/gzip 和轻量同步头。原显示、排序和交互已进行前后对照。

**仍保留的成本：** 首次进入仍生成全部内容；真实阵容变化时保留整页初始化；X 页面有完整刷新路径。完整 `view()` 还构建本队卡库、榜单、近期赛事、市场、预测、邮件等多个子系统。球员目录虽有缓存，失效粒度较粗；`ownTeamView()` 会反复查询同名卡和计算回收预览。代码规模约为服务 12,000 行、前台 8,000 行，跨系统状态依赖多。

**优先优化：**

1. 加入分阶段时间和事件循环延迟记录，区分计算、读盘、序列化、压缩、传输、DOM 更新与绘制。
2. 对未变化数据按领域 revision 复用，建立 owner/player/card 索引；缓存键包含权限、账号和有效规则版本。
3. 继续用紧凑响应及按需详情，保留相同前台内容。无变化轮询不能触发全量派生与写盘。
4. 核验同步 JSON/压缩、登录哈希、整轮结算和集中邮件/发奖的长任务；将可分批处理的工作放入已有队列或有界切片。
5. 对“多观众同场直播 + 阵容编辑 + 批量卡牌 + 自动结算”组合压测，观察 p50/p95/p99、长任务、请求量、内存和队列长度。

以上是待测热点和实施顺序，不是已测得的容量瓶颈。切换框架、大规模重写或改变列表显示方式都不是当前证据支持的第一步。

## 5. 优化实施路线

### 阶段 A：建立可信基线，先保护现有玩法

1. 按已确定范围整理：世界杯和主教练永久废弃，下架扩容与独立旧房间分别标记；同步入口、路由、文档与测试，不重建废弃玩法。
2. 将完整测试拆到赛事、战术、资产、经济、运维等领域；所有可写状态路径隔离，使用版本化固定内容夹具。
3. 对 19 项已观察失败做逐项归因；需要修测试的与需要修业务的分开记录，优先解决轮换、奖励与赛程。
4. 给现有玩家流程建立可复现存档快照与关键结果，不改变 UI 布局或游戏规则。

**验收：** 当前规则的测试能在干净环境稳定运行；所有已支持路由都能落到服务实现；联赛/杯赛/总决赛有完整结算基线。旧版本保留独立兼容检查。

### 阶段 B：继续等价性能优化

1. 使用小、中、大资产存档，测量完整视图、轻量视图、目录、历史和直播的构建/序列化成本。
2. 按领域 revision 缓存公共视图和派生数据；建立资产与活跃任务索引。
3. 减少无变化刷新、无变化写盘、重复压缩和集中结算长任务；核验队列吞吐和事件循环延迟。
4. 对 X、阵容真实变动和首次进入页面单独剖析，保留原显示内容、排序、表单状态和操作方式。

**验收：** 在同一存档/快照下前后比较，内容、布局、表单、滚动和动作结果一致；报告 p95/p99、长任务、请求数、内存和后端排队。对没有提速的场景如实记录，不把脚本耗时当作 FPS。

### 阶段 C：强化一致性与恢复能力

1. 统一经济操作的业务 ID、重试语义和对账；覆盖开包、买卖、交换、强化、X、赞助和发奖。
2. 做跨日、崩溃、恢复、重复任务和节点掉线演练。
3. 规范内容发布、缓存失效、审计和恢复流程。
4. 完成会话撤销和账号规则整治，验证已有设备的兼容迁移。

**验收：** 故障前后金币、资产、任务和比赛状态可对账；重试不重复扣费/发奖；恢复后的对局与采样序列符合规定；被撤销凭证无法继续操作。

### 阶段 D：验证 V3 战术价值和长期经营

1. 使用真实卡池、强化、X、特性和羁绊，完成配对战术矩阵及多种能力差实验。
2. 在同一 V3 分布下验证预测市场、奖励、经营收入与培养消耗。
3. 观察强度优势、战术应对、平局率、意外事件和成长速度，确定是否需要下一轮规则调整。
4. 分别验收网页、离线包、Android TV 和 Worker 的实际引擎版本与契约。

**验收：** 能说明典型战术的收益、代价与应对；长期样本中数值有价值但不独占结果；预测和赛季经济有可重复的统计依据；平台交付有实际包与验证记录。

### 实施边界

本次仅形成评估及证据，没有修改游戏逻辑。后续默认优先进行等价的请求、计算、渲染、缓存、索引和可靠性优化。改概率、奖励、价格、成长速度、名单规则，以及扩展俱乐部经营，应独立列项；不能夹带在性能重构中。世界杯和主教练已永久退出建设范围。
