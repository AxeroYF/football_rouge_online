## 2. 实际使用的方案

**`shield-v1`：SVG 分层盾形卡框，卡面比例 `26/35`。** 这套是网页 DOM/CSS/SVG 实现，适合 YFFM1 现有技术结构。

| 类型 | 原方案 |
| --- | --- |
| S | 蓝/金 |
| A | 青绿/银 |
| B | 梅紫/铜 |
| C | 松绿/灰绿 |
| X | 原 Rougelite 复用 S 主题，等级文字仍显示 X |
| +9 | 独立紫色强化边框，S/X 使用红金高强化背景 |
| +10 | 独立金色强化边框，S/X 使用红金高强化背景 |

主要层次是背景、可选粒子层、人物、底部铭牌、信息/国旗/队徽、等级/强化、边框、特性文字。S/X 人物层在边框与信息之上，形成穿层效果；其他级别人物位于铭牌与边框之下。原实现还含 hover 扫光、强化边缘扫光，以及静态/延迟渲染能力。

该方案没有必要为每张球员卡生成整张合成图片。边框和背景资源可以缓存，名字、能力、等级和特性保持为动态文本/节点。

## 3. 对 YFFM1 的接入评价

**建议采用卡框视觉与分层方式，保留 YFFM1 当前的数据、动作和比赛规则。** 不宜直接把 Rougelite 整套卡牌业务模块复制进来。

| 接入点 | YFFM1 现状 | 适配要求 |
| --- | --- | --- |
| 统一入口 | `s4PlayerCardMarkup()` 被多处调用 | 建立统一适配层，避免背包、强化、市场分别重写 |
| 总评 | 优先使用具体卡/球员的有效总评 | 仍采用当前优先级，不从 Rougelite 导入额外能力算法 |
| 卡实例 | 具体卡 ID 与球员定义 ID 并存 | 分开传 `playerId`、`cardInstanceId`，DOM key 保持稳定 |
| 人物卡画 | `cardProfile` / 传奇/A/X 配置；字段为 `xPercent/yPercent/widthPercent` | 映射到 `art.x/y/width`，复用原图片路径；新比例下校准裁切 |
| 特性 | 本地特性名和有效特性来源 | 用本地规则解析，不引用 Rougelite 的引擎特性库 |
| 强化等级 | 当前卡实例等级与有效能力 | 仅改变对应框/标记，不改变概率、材料、加成或上限 |
| 金球奖 | YFFM1 原有星标/获奖次数 | 必须保留，原盾形生成器没有覆盖该业务标记 |
| X | 本地独立身份与可成长数据 | 保留 X 级识别和数据，不能因为共用 S 主题而变成 S |
| 交互 | button 属性、选卡、拖动、弹窗、市场/交换动作 | 保留现有 data 属性、事件入口、可访问名称和禁用状态 |
| 增量更新 | 现有局部更新会查询旧子节点选择器 | 同步适配总评/等级/特性等补丁，不能只替换 HTML 后让后续刷新失效 |
| 资源路由 | 前台资源位于 `/versus/` | 将原硬编码 `/assets/` 映射为 `/versus/assets/` 或显式资源基址 |
| 布局 | 现有不同场景的卡位与密度 | 按场景给定宽度和卡位，检查新比例；不整体修改导航、排序或操作逻辑 |

静态参考源码中的共享契约依赖 `engine/s4-v2.1/versus/trait-pool.js`，资料窗还引用 Rougelite 的成本与属性配置。这里的“引用”是原项目依赖，不应作为 YFFM1 接入时导入另一套引擎的理由。最小视觉入口是 `card-shield-markup.js`，其数据由本地适配层提供。

### 人物遮挡是需要单独验收的事项

新盾形比例与旧卡不同；直接复用 YFFM1 人物坐标时，传奇大图会盖住姓名或铭牌。这是 Rougelite 的人物穿层表现，用户已明确要求保留：S/X 卡画位于底板和姓名之上，不在铭牌上沿裁切。其他等级保留现有信息保护；完整姓名继续保存在卡片的可访问名称及详情中。

## 4. 性能策略

原 Rougelite 已考虑卡片规模：单一动效控制器/RAF、可见性检测、页面隐藏停止、低动态偏好、位图尺寸限制、延迟挂载和分批处理。这些可以参考，但必须适配 YFFM1 现有节点复用与滚动容器。

建议默认分配：

| 场景 | 推荐方式 | 约束 |
| --- | --- | --- |
| 战术板与直播磁贴 | 静态或更轻的既有变体 | 不为 22 名场上球员持续新增粒子画布 |
| 背包、强化仓库、市场大列表 | 静态框，图片懒加载；必要时按可见范围挂载卡面 | 保持原卡位、排序、滚动和可点击区域；不要每次选卡重建全列表 |
| 球员详情/少量候选卡 | 可选可见卡动效 | 共用控制器，切页/隐藏/减弱动画时停止 |
| 高强化框 | SVG 边框默认静态 | 扫光是可选表现，不可让数百个离屏卡持续工作 |

需要关注的代价是：每张卡至少多张分层图片、SVG 信息、阴影与裁切；资源缓存只解决网络复用，不能自动消除每个节点的布局、合成与绘制成本。正式迁移前应在同一大存档下测量。

## 6. 正式迁移顺序与验收

1. 明确卡框资产版本和资源基址，保留原始快照；增加本地只读卡面适配层。
2. 在详情和少量候选卡验证字段、缺图、长名字、X、特性、多次金球奖、+9/+10 和人物遮挡。
3. 接入背包与强化，保留 DOM key、选中态、材料资格、事件属性和增量补丁。
4. 接入市场/交换及球员目录，逐项核对不同实例与有效能力；小卡/磁贴保持适合场景的密度。
5. 在桌面和真实移动设备、大卡库、直播同时运行等场景对比，必要时限制可见动效。

**功能验收：** 原操作全部可执行，保存/交易/强化结果不变，显示信息不丢，球员与卡实例不混淆，人物与金球奖标记可识别。

**性能验收：** 同存档测首次进入、滚动、连续选卡、重复刷新、切页和隐藏后的请求/RAF；检查节点复用、长任务、内存、图片解码和卡面是否正确更新。没有数据支持时不承诺“新卡框更快”。

以上第 1—6 节保留原始评估与迁移要求。正式实施状态如下。

## 7. 已接入正式游戏（2026-11-04）

`s4PlayerCardMarkup()` 统一调用 `versus/public/player-card-shield.js`，使用原盾形生成逻辑、26/35 比例与 S/X 蓝金、A 青绿银、B 梅紫铜、C 松绿灰配色。16 个 SVG 图层已原样复制到 `versus/public/assets/card-frames/shield-v1/`，与固定提交的 Git blob SHA-1 全部吻合；原始参考快照未改。

这次更正区分卡包包装与球员卡面：包装继续原样，开包、选秀、背包、详情、强化、市场、交换、球员目录和正式荣誉卡等统一渲染器的调用方使用盾形。七人制原型和独立的荣誉室演示页不在正式游戏的统一渲染入口内，未随之迁移。

适配保留当前卡实例的有效总评、强化等级、特性、金球奖次数、X 身份，以及点击/拖动/禁用所需的原 data 属性。按用户更正，S/X 恢复 Rougelite 原始层级：底板 z=3、姓名/信息 z=4、强化标记 z=6、边框 z=7、人物 z=8；撤销额外的底部人物裁切，允许卡画覆盖姓名区域。其他等级仍保留既有信息保护。手机强化槽按原有 90px 高卡位缩放盾形，侧边保留同一球员的姓名、等级和能力，防止卡面覆盖强化操作。

国旗和俱乐部标记映射到已经存在的本地资源；没有对应资源时使用原方案的文字回退，不引入缺失图片请求。卡框采用共享 SVG 图片缓存，不为卡牌列表新建粒子画布或持续运行的卡面 JavaScript 动画。图片加载保留 eager/lazy 场景差异，不把所有列表头像都提升为高优先级。开包舞台原有的有限入场效果继续工作。

未更改价格、概率、球员属性计算、强化规则及上限；+9/+10 原资源保留，不开放新的强化等级。
