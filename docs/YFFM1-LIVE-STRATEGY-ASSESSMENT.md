# YFFM1 赛事直播策略评估

日期：2026-11-12。依据：当前源码、已有观赛实现和隔离内存比赛探针。本轮是评估，未修改直播运行逻辑或真实存档。

## 总体判断

当前采用服务器分步推进、观众快照读取、阵型与文字事件展示的策略，适合以经营和预设战术为核心的 YFFM1。服务器推进与观赛读取分离这一基础值得保留。

优先改造方向是比赛过程的可解释性、关键事件的观看节奏，以及观赛恢复和状态同步的完整性。整场连续球员动画不是本轮必要前提。

## 当前实际流程

1. 服务器默认每 100ms 调用 advanceLiveSlice，配置范围为 100–2000ms。联赛和杯赛显式限制每次最多一场、每场一条控球链，正式赛事优先，空闲切片在友谊赛与 AI 训练之间轮转。总决赛分支的场次上限存在遗漏，详见下文。
2. 当前 V3 正式比赛沿用 YDL 引擎适配器：常规比赛 120 秒映射 180 条控球链；推进目标由墙钟时间决定，再由切片预算逐步追赶。补时、加时和点球另按当前规则处理。
3. 联赛观众约在上次请求完成 700ms 后读取下一份快照；这不是固定 700ms 的到达间隔。后台暂停轮询，恢复前台立即读取；失败指数退避，最多重试 5 次。
4. 联赛直播读取不负责推进模拟。当前代码里的 SSE 通道主要属于另一条房间流程，不能把它当成联赛观赛已经采用推送的证据。
5. 前端展示比分、整数分钟、球员阵型/状态、最新事件、事件列表和统计。使用 DOM 节点复用、渲染指纹跳过重复更新，并保留用户浏览历史事件时的滚动位置。
6. 正式赛事默认关闭圆点回放数据；比赛状态有独立检查点，默认间隔 30 秒并错峰写入，结算另行排队。

主要源码：devtool/server.js；versus/league-service.js；versus/v2/ydl-league-engine-adapter.js；versus/public/app.js。

## 已有优势

- **模拟成本与观众人数解耦。** 同一场比赛由服务器推进，观众读取共享的比赛状态，不各自生成比赛结果。观众数量仍会增加快照构建、序列化、压缩和网络工作量。
- **推进切片合理。** 多场比赛轮转，减少一次请求或一个定时回调中集中推进大量比赛的风险；比赛完成后的结算也有独立调度。
- **常规观赛更新频率基本合适。** 每场平均每秒 1.5 条控球链，约 700ms 的轮询已接近事件更新节奏。提高请求频率不会自动补出真实的球和球员运动。
- **已有前端优化应保留。** 持久背景、节点复用、事件滚动保留、后台暂停和过期响应拦截都适合作为重建基础。
- **稳定性有基础。** 检查点和赛后归档提供了恢复与收尾机制；重启后未来随机过程的一致性仍应作为独立验收项，不能仅凭链索引恢复就认定完整确定性。

## 主要问题

### 1. 球场主要承担阵型展示，过程反馈不足

直播球员位置主要来自 team.positions，前端又将两队映射到同一球场的两个半场。这能说明谁在什么位置、谁进球或被罚下，但没有持续表达球的流向、接应、压迫、推进与退防。

因此当前观看价值主要集中在文字和统计。球队为什么获得机会、战术如何影响这次结果，需要更明确的反馈。

建议定位为“足球经理式转播”：保留清楚的阵型与球员状态，增加关键控球链的轻量示意，示意数据绑定真实参与者、阶段位置和事件结果。

### 2. 常规推进很快，关键事件缺少独立观看节奏

常规比赛约两分钟，事件更新较密集。目前顶部强调条直接取最后一条事件，重要事件可能被后续普通播报很快替换；完整事件仍在列表中，但视觉焦点不保证保留。

建议区分关键事件、战术事件和普通进程：

- 进球、点球、红牌、伤退等给予独立的短时强调。
- 战术切换与其触发条件关联显示。
- 普通推进保持简洁，允许用户展开细节。

这些展示节奏不应阻塞服务器继续推进比赛。球场、字幕、比分与统计需要使用同一份比赛状态和事件序列。

### 3. 新战术原则尚未充分进入直播语言

当前转播策略摘要主要展示旧心态、单一打法与阵型。新版组织方式、防守区块、得球策略和对抗强度，缺少明确的当前状态及效果说明。

优先增加：

- 当前预案：默认、领先或落后，何时切换。
- 当前生效的战术原则。
- 近期关键机会与球员、线路、失误的关联。
- 赛后总结与相同事件和数据口径对应。

涉及完整战术镜像时，沿用现有对手战术细节保护规则。

### 4. 后台暂停与会话清理存在恢复缺口

前端切后台后暂停观赛轮询；服务器会清理 30 秒未心跳的观众。如果其他观众或直播列表读取触发清理，用户回到前台后仍拿旧 token 重试，最终可能退出直播。

隔离探针已复现：创建观赛会话，时间前进 31 秒，读取直播列表触发清理，再用原 token 读取，返回“观赛会话已过期，请重新进入直播”。

建议将网络波动和会话过期分开处理。公开赛事可自动重新入场；私有 AI 训练应通过创建者身份恢复权限。观众在线人数清理与用户恢复资格也应分开设计。

### 5. 渲染指纹未覆盖全部已展示字段

renderBroadcast 的指纹包含比分、分钟、事件数/末事件 ID、在场人数、站位、观众和背景，但不包含球员体力、评分和比赛统计的全部值。

用构造的快照修改统计、体力和评分，同时保留指纹字段，指纹结果不变。这证明仅有这些字段变化的更新可被当前跳过条件忽略；它不是对真实赛事中发生频率的测量。

建议服务端提供覆盖公开直播状态的 revision，前端据此决定刷新；也可先补齐指纹覆盖，明确各块更新条件。

### 6. 总决赛分支没有完整传递切片场次预算

advanceLiveSlice 对联赛和杯赛传入 maximumMatches:1，对总决赛只传 maximumChainsPerMatch:1。总决赛内部仍调用 liveAdvanceBatch，而该方法在场次预算缺失时默认为 Infinity。

所以“全局每个切片最多一条链”的意图没有覆盖所有路径：存在多场待推进的总决赛比赛时，一个切片可以处理多场。应统一预算传递，并补充跨赛事场景，避免性能预期只在联赛路径成立。

## 调度预算与成本

常规一轮五场的理论需求：

- 5 × 180 / 120 = 每秒 7.5 条控球链。
- 默认联赛路径 100ms 一个切片、每次最多一条，理论上限为每秒 10 条。
- 理想情况下剩余约每秒 2.5 条，供辅助比赛、切换和额外工作使用。

这是调度预算的算术上限，不是服务器实测吞吐。单链耗时、事件循环延迟、快照生成、存盘与结算都会影响实际余量。两个同时按标准节奏运行的辅助比赛平均需要额外每秒 3 条链，已超过上述理想余量，可能出现追赶。

因此不能随意把切片间隔调长，再继续承诺两分钟内完成整轮。若要支持更多同时进行的训练和友谊赛，应先测量落后目标链数与 CPU 占用，再决定独立计算预算、任务调度或执行隔离。

快照探针使用一场隔离 V3 比赛：

| 比赛进度 | 控球链 | 事件数 | JSON 原始字节 | gzip 字节 |
| --- | ---: | ---: | ---: | ---: |
| 开场 | 0 | 0 | 19,142 | 2,856 |
| 45 分钟 | 90 | 84 | 51,310 | 7,441 |
| 90 分钟显示、尚未终场 | 179 | 139 | 73,489 | 9,289 |

现有 HTTP JSON 返回已支持 gzip。这个样本不说明带宽已经成为瓶颈；更值得观察的是同场多观众时重复快照构建和逐请求同步压缩的 CPU 成本。

可以先按比赛 revision 复用公共快照和压缩内容，将观众列表/权限相关字段单独处理；再评估增量事件或单向推送。更换传输方式本身不解决重复构建和过重快照。

## 建议优先级

| 优先级 | 工作 | 验收要点 |
| --- | --- | --- |
| P0 | 后台返回、断线和过期会话恢复 | 公开观赛自动恢复；私有训练权限正确；无重复会话和重复扣费 |
| P0 | revision/刷新完整性 | 比分、统计、体力、评分、阵型和比赛阶段同步，旧响应不覆盖新状态 |
| P1 | 关键事件层级与转播节奏 | 重要事件有足够阅读时间，普通事件不断流，服务器推进不被客户端演出阻塞 |
| P1 | 新战术原则与预案展示 | 能看懂当前执行什么策略、何时切换，以及事件依据 |
| P1 | 多观众与多赛事组合测量 | 链落后量、事件循环延迟、快照构建耗时、响应大小、前端更新时间 |
| P1 | 全赛事调度预算一致性 | 总决赛也显式受场次上限约束，主赛与辅助赛满足约定的优先级和追赶策略 |
| P2 | 关键回合轻量可视化 | 真实事件、参与者和位置一致；手机有轻量模式；保存量有预算 |
| P2 | 按需增量/推送与快照共享 | 先有测量，验证重复工作量下降及恢复、补帧完整性 |

推荐保留当前权威模拟和切片机制，把下一版直播做成“看得懂战术与关键回合的转播”。视觉重建中的赛事转播方向可以服务于这一目标。
