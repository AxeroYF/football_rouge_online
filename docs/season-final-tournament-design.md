# 赛季总决赛设计稿

## 1. 赛事定位

赛季总决赛是每个赛季在联赛、杯赛结束后进行的第三项正式赛事。

赛事必须拥有独立的：

- 赛事状态与生命周期
- 赛程、对阵和晋级树
- 比赛记录与统计
- 奖励结算
- 玩家端页面
- 管理后台入口
- 赛季历史归档

赛季总决赛不直接复用联赛页面或杯赛页面作为主要容器，但比赛执行、伤停、停赛、阵容和战术逻辑可以复用现有比赛引擎。

## 2. 参赛队伍

- 共 10 支球队。
- 9 支玩家球队。
- 1 支 AI 球队。
- AI 固定为 `10 号种子`，不参与玩家球队之间的综合种子竞争。

## 3. 综合种子

联赛和杯赛结束后，先分别确定联赛成绩和杯赛成绩，再生成赛季总决赛种子。

### 3.1 联赛成绩

联赛成绩直接根据最终排名确定：

```text
联赛第 1 名 > 联赛第 2 名 > ... > 联赛第 10 名
```

联赛权重为 `60%`。

### 3.2 杯赛成绩

杯赛成绩按照以下优先级排序：

1. 淘汰赛阶段走得更远的球队优先。
2. 如果两队在同一淘汰赛阶段出局，则比较杯赛小组赛最终排名。
3. 没有进入淘汰赛的球队，直接按照杯赛小组赛最终排名。
4. 若淘汰赛阶段和小组赛排名都相同，使用稳定的球队 ID 作为最终兜底排序。

杯赛成绩示意：

```text
杯赛冠军
> 杯赛决赛负者
> 半决赛负者
> 四分之一决赛负者
> 更早轮次被淘汰者
> 未进入淘汰赛的球队
```

杯赛权重为 `40%`。

### 3.3 综合分与种子

建议先将联赛排名和杯赛成绩分别转换为同一尺度的标准成绩分：

```text
综合分 = 联赛成绩分 × 0.60 + 杯赛成绩分 × 0.40
```

玩家球队按综合分从高到低获得 `1-9 号种子`，AI 固定为 `10 号种子`。

玩家球队综合分相同时，按以下顺序破同分：

1. 联赛最终排名
2. 杯赛小组赛最终排名
3. 稳定的 `teamId` 字典序

最终种子结果必须保存联赛排名、杯赛成绩、综合分、种子号和破同分依据，保证赛季重载后结果不变化。

## 4. 双败赛制结构

这是一个由联赛和杯赛成绩衍生出的非标准 10 队双败淘汰赛，不应实现为普通单败淘汰赛，也不应把所有球队放入胜者组。

### 4.1 初始位置

```text
1 号种子 -> W2
2 号种子、3 号种子 -> W1
4 号种子 -> B4
5-10 号种子 -> B1、B2、B3
```

### 4.2 胜者组

#### W1：胜者组半决赛

- `2 号种子 vs 3 号种子`
- 胜者进入 `W2`
- 败者掉入败者组 `B7`

#### W2：胜者组决赛

- `1 号种子 vs W1 胜者`
- 胜者成为胜者组冠军，进入最终决赛
- 败者掉入败者组 `B8`

### 4.3 败者组

#### B1：败者组首轮

- `5 号种子 vs 10 号种子`
- 败者淘汰
- 胜者进入 `B5`

#### B2：败者组首轮

- `6 号种子 vs 9 号种子`
- 败者淘汰
- 胜者进入 `B5`

#### B3：败者组首轮

- `7 号种子 vs 8 号种子`
- 败者淘汰
- 胜者进入 `B4`

#### B4：败者组第二轮

- `4 号种子 vs B3 胜者`
- 败者淘汰
- 胜者进入 `B6`

#### B5：败者组第二轮

- `B1 胜者 vs B2 胜者`
- 败者淘汰
- 胜者进入 `B6`

#### B6：败者组第三轮

- `B4 胜者 vs B5 胜者`
- 败者淘汰
- 胜者进入 `B7`

#### B7：败者组第四轮

- `B6 胜者 vs W1 败者`
- 败者淘汰
- 胜者进入 `B8`

#### B8：败者组决赛

- `B7 胜者 vs W2 败者`
- 败者淘汰
- 胜者成为败者组冠军，进入最终决赛

### 4.4 晋级关系总表

```text
W1 胜者 -> W2
W1 败者 -> B7
W2 胜者 -> 最终决赛
W2 败者 -> B8

B1 胜者 -> B5
B2 胜者 -> B5
B3 胜者 -> B4
B4 胜者 -> B6
B5 胜者 -> B6
B6 胜者 -> B7
B7 胜者 -> B8
B8 胜者 -> 最终决赛
```

## 5. 最终决赛

最终决赛由胜者组冠军和败者组冠军进行两回合淘汰赛。

### 5.1 两回合规则

- 第一回合：胜者组冠军 vs 败者组冠军。
- 第二回合：败者组冠军 vs 胜者组冠军。
- 不计算客场进球。
- 两回合总比分相同，第二回合结束后进入加时。
- 加时仍平局，进入点球大战。
- 第二回合结束并完成加时或点球后，确定赛季总决赛冠军。
- 不使用 Reset Final。

### 5.2 阵容与战术

- 两回合允许使用不同阵容。
- 两回合允许使用不同战术方案。
- 两回合之间不重新解除禁用球员。
- 第一回合产生的伤病和停赛跨回合保留。
- 第二回合开始前，系统必须根据第一回合后的实际状态校验可出场球员。

## 6. 决赛前状态刷新

两支进入最终决赛的球队，在第一回合开始前执行一次决赛状态刷新：

1. 清除进入决赛前已有的伤病。
2. 恢复双方决赛初始体力。
3. 应用双方最终锁定的禁用名单。
4. 锁定第一回合可用阵容与战术。
5. 创建并开始第一回合比赛。

刷新只发生在最终决赛开始前，不在第二回合开始前重复刷新。

第一回合结束后产生的内容跨回合保留：

- 比赛内伤病与伤退
- 正式停赛
- 红牌停赛
- 其他影响下一场正式比赛的状态

## 7. 决赛球员禁用

最终决赛双方各自禁用对手 3 名球员。

### 7.1 禁用名额

每方必须选择：

- 前场球员 1 名
- 中场球员 1 名
- 后场球员 1 名

球员分类按照球员的主位置，不按照本场临时安排位置。门将不属于三条线名额，不能占用禁用名额。

被禁用球员在最终决赛两回合均不能：

- 首发
- 替补登场
- 进入有效比赛阵容

### 7.2 异步邮件流程

1. `B8` 结束并确定最终决赛双方。
2. 系统分别向双方发送禁用邮件。
3. 玩家可以异步提交禁用选择。
4. 禁用统一在第一回合开赛前 10 分钟锁定。
5. 已提交的一方使用玩家选择。
6. 未提交的一方由系统随机选择前场、中场、后场各 1 名球员。
7. 锁定后，双方都收到通知邮件，明确自己被对方禁用的球员。
8. 禁用结果同时作用于最终决赛两回合。

建议保存如下状态：

```ts
type FinalBanDecision = {
  tournamentId: string;
  finalTieId: string;
  fromTeamId: string;
  targetTeamId: string;
  bannedPlayerIds: {
    forward: string;
    midfield: string;
    defense: string;
  };
  source: "player" | "system-random";
  submittedAt: number | null;
  lockedAt: number;
};
```

### 7.3 禁用异常处理

实现时需要处理：

- 对方某条线没有可用球员。
- 球员主位置不明确。
- 球员在禁用锁定前被释放、交易或失去所有权。
- 球员在锁定后发生伤病或停赛。
- 玩家重复提交或修改已锁定的选择。

建议在锁定瞬间重新校验球员所有权、主位置和可用状态；无效选择由系统在同一条线重新随机补齐。

## 8. 时间安排

联赛最后一轮在北京时间 `15:40` 结束，赛季总决赛第一场从 `16:00` 开始。

普通轮次之间间隔 15 分钟，胜者组和对应的败者组错开：

| 时间 | 比赛 |
|---|---|
| 16:00 | W1 |
| 16:15 | B1、B2、B3 |
| 16:30 | W2 |
| 16:45 | B4、B5 |
| 17:00 | B6 |
| 17:15 | B7 |
| 17:30 | B8 |
| 17:30 | 确定决赛双方并发送禁用邮件 |
| 17:40 | 禁用截止，系统随机补齐未提交选择 |
| 17:50 | 决赛第一回合 |
| 18:00 | 决赛第二回合 |

决赛两回合计划间隔为 10 分钟。

如果任一前置比赛实际进入加时或点球并超过计划时段，依赖该结果的后续比赛必须顺延到下一合法时间槽，不能使用未完成的比赛结果。

## 9. 推荐核心状态

```ts
type SeasonFinalTournamentState = {
  id: string;
  seasonId: string;
  status: "scheduled" | "running" | "final" | "completed" | "cancelled";
  createdAt: number;
  seedSnapshot: SeedSnapshot[];
  bracket: BracketNode[];
  matches: SeasonFinalMatch[];
  finalTie: {
    winnerBracketChampionId: string | null;
    loserBracketChampionId: string | null;
    firstLegId: string | null;
    secondLegId: string | null;
    aggregateScore: [number, number] | null;
    extraTime: boolean;
    penalties: boolean;
    championId: string | null;
  };
  finalBanDecisions: FinalBanDecision[];
  stateRefreshAt: number | null;
};
```

## 10. 页面要求

赛季总决赛需要独立页面，建议包含：

- 赛事状态和当前阶段
- 综合种子排名及联赛/杯赛成绩拆解
- 胜者组 bracket
- 败者组 bracket
- 最终决赛两回合比分
- 禁用状态和禁用截止时间
- 伤停、停赛和可出场阵容状态
- 已完成比赛、下一场比赛和晋级流向
- 最终冠军与赛季奖励

颜色建议：

- 胜者组：蓝色
- 败者组：红色
- 最终决赛：金色或高亮色
- 已淘汰球队：低透明度或灰色
- 待定晋级位：使用来源标签，例如 `W1胜者`、`B3胜者`

## 11. 开发前必须固化的规则

以下内容在开始编码前必须写入参数或规则常量：

1. 联赛排名分和杯赛成绩分的标准化方法。
2. 杯赛“走得更远”的阶段排序枚举。
3. 杯赛小组赛排名的同分处理方式。
4. 球员主位置到“前场/中场/后场”的映射表。
5. 球员禁用锁定后的交易、释放和失去所有权处理。
6. 前置比赛加时或点球导致赛程顺延的规则。
7. 最终决赛两回合的主客场固定方式。
8. 最终决赛奖励内容和结算幂等键。
