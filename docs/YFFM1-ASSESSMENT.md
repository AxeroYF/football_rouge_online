# YFFM1 整体评估

评估日期：2026-11-03。范围：S4 最终归档源码、本地运行、代码结构、数据安全、测试基线、性能风险及更名方案。本轮按“先整体评估”执行，没有修改游戏实现、比赛数值、存档格式或线上服务。

## 结论

建议以现有比赛引擎、球员库和联赛规则为基础，分阶段整理为 YFFM1。功能已形成完整的足球经营游戏；当前最需要重建的是可靠的工程基线：明确实际运行源码、修复账号持久化和战术版本问题、恢复可信的回归检查，然后进行模块拆分和性能优化。

S4 的业务代码已经有轻量同步、分片存储、直播切片及部分轻量变更响应。下一轮优化应接着这些机制推进。当前没有足够的线上负载或真实存档样本，可以据此承诺性能提升比例或并发容量。

## 已复现或由源码明确确认的问题

### P0：账号库损坏后存在覆盖风险

`versus/room-service.js:251–270` 在账号文件解析失败时清空内存账号集合，随后 `saveAccounts()` 直接覆盖原 JSON。使用临时损坏文件复现：构造服务成功、被视作空库，注册后原损坏文件被新账号内容覆盖。故障发生时应停止对该存档的写入，并提供明确恢复路径。

账号保存缺少联赛存储已有的临时文件、同步落盘和替换机制。另一个故障注入确认：注册写盘抛错后，新账号仍留在内存，成功状态与落盘状态不一致。建议作为 YFFM1 第一批修复，覆盖读取失败、写盘失败、重启恢复与重试。

证据：`.assessment/account-probes/report.json`。这些操作只使用测试夹具。

### P1：阵容码导入使方案版本号倒退

`versus/league-service.js:6331` 的导入路径重新生成方案快照并覆盖当前方案，未按正常保存路径推进 revision。内存夹具复现结果：当前 revision 为 9，导入后变为 0。

这会破坏用于多端保存的版本比较前提。应让导入、普通保存和方案切换采用统一的冲突检测与版本推进规则，同时验证旧自动保存请求不会覆盖新导入结果。

证据：`.assessment/model-probes.json`。前端导入前已有 flush 等待，不应把该问题简化为前端没有等待保存。

### P1：后台仍有历史默认密码回退

`versus/admin-api.js:19` 在没有环境配置时使用硬编码后台密码。后台已有登录限流和会话检查，但默认密码仍可能被新部署沿用。建议明确开发/生产配置，生产启动必须有显式凭据；更名时同时补齐环境变量示例。报告不重复公开默认密码。

### P1：回归基线尚未建立

默认测试入口仅覆盖 `test/` 下 59 个文件；根目录另有 12 个测试文件，其中一些针对旧副本。应先识别有效覆盖和旧快照，再统一测试发现规则，不能直接把所有历史测试无差别加入。

当前失败混合了多种原因：

- 数据预期过期：例如后台测试预期 676 名球员，实际 723 名。
- 测试夹具未同步：荣誉室案例缺少已新增的赛季总决赛结束条件；YOOGLE 使用动态抽取的函数却未提供 `offlineAttributeSettings`。
- 需要核对规则与实现：伤退替补未继承测试预期的 `targetForward` 职责；属性快照和若干球员资产案例的预期与实际不同。
- 内容覆盖存储测试在并行诊断中发生 Windows 文件锁错误；单独复查仍有持久化锁错误及旧特性数量断言不一致，需要继续定位。

不能通过统一修改期望值把这些情况变成“全部通过”。应逐项决定有效行为，先建立可复现夹具，再修改实现或过期测试。

### P2：展示配置与实际引擎选择不一致

无额外引擎环境变量的本地服务，`/api/versus/config` 返回 `matchEngine: v1`；同样的默认规则下，实际联赛生成的是 `version: 2`、`match-engine-v2.1`。服务入口和联赛各自推导配置，应统一配置来源。该发现不表示联赛实际运行了 V1。

## 性能评估与边界

已经存在的优化包括：联赛 head 轻量查询、部分 compact 变更响应、球员目录缓存、分片增量保存、直播分步推进和局部 UI 刷新。保留这些成果，先采样再定位后续瓶颈。

优先测量以下路径：

1. `view()`、后台概况和直播快照的构建/序列化时间及响应体积。
2. 账号同步写盘、联赛结算、manifest 清理和赛季归档期间的事件循环延迟。
3. 大量球员卡、背包及市场条目的 DOM 数量和整页重绘成本。
4. 多客户端同时观赛时的快照复用、请求频率和断线恢复。

建议指标是接口 P50/P95、事件循环延迟、CPU、内存、单次写盘字节数/时长、可见卡片数量。先做本地固定数据集，再在与目标服务器相近的环境复测。当前没有做真实浏览器交互 QA、正式服采样或完整赛季负载验证。

## 推荐实施顺序与验收

1. **建立 YFFM1 基线。** 整理启动说明和配置；明确 S4 联赛为主体及保留的附属模式；完成显示名/工程包名更名；修复账号故障路径、阵容版本推进和配置分歧；清理过期测试，给长运行测试独立入口。验收：干净检出可启动、注册/登录与重启后资产一致、故障写入不覆盖原档、阵容导入不倒退版本、核心回归可稳定完成。
2. **拆分职责。** 先抽出配置、公开视图、HTTP 路由与前端纯展示逻辑，再按球队战术、球员资产、赛事、交易、历史归档分离服务。保持原生 ESM 和现有引擎作为起点；每批改动使用固定种子与存档夹具对照。验收：来源唯一、依赖方向清楚、保存与结算行为不变。
3. **按数据优化性能。** 用固定小/大存档和多客户端观赛场景建立测量，针对确认的热点做分页、增量响应、局部渲染和写盘调度。异步化存储前先设计失败确认、写入队列和恢复协议。验收：同一场景下可比较的性能指标改善，正确性检查仍通过。
4. **独立迭代产品。** 在工程基线稳定后再评估玩法、赛制、经济、卡牌、界面和引擎平衡；每轮明确目标并留存可比较的模拟结果。

本轮交付是评估与本地源码准备。正式更名、重构、删除历史模式、数据重置和远程发布都尚未实施。
