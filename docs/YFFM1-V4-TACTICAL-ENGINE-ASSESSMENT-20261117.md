# YFFM1 V4 比赛引擎重做评估

日期：2026-11-17（Asia/Shanghai）。范围：基于当前工作区源码的架构评估，未实施引擎重做、修改正式存档、启动或部署服务。本轮没有重新运行引擎测试或性能测试，以下设计与验收目标不是实测结果。

用户目标：以战术为完整导向，增加可解释性，为后续小圆点实时比赛展示打基础。观看方式已确认：可调速，关键片段慢放。

## 1. 结论与重做边界

建议建立独立 V4 内核：战术约束与意图 → 球员决策及协同 → 位置与球路演进 → 对抗/规则判定 → 比赛事件。解释、统计和画面共同读取这条事实链。

“完全重做”适用于比赛内核，不意味着重写账号、资产、卡包、联赛、杯赛或已批准的球员数据。旧引擎留作旧比赛恢复与对照，新内核不再以 V2 阶段概率结算为中心。

战术决定怎样制造和应对局面，球员能力决定识别与执行的水平，对手会同时响应，随机性保留在有依据的判断误差与技术执行中。不能把战术导向解释为弱队只要选中克制按钮就必胜，或所有球员百分之百照脚本跑位。

推荐中等精度的二维空间模拟，球可有高度与飞行时间，球员有真实位置、速度、朝向和行动状态。暂不需要人体骨骼、完整碰撞物理或高频三维模拟。区域网格继续用于查询和汇总，具体传接球与拦截以空间和时间为依据。

| 路线 | 与目标匹配程度 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| V3.3 继续扩充参数和解说 | 可以改善局部反馈 | 行动链结算与连续画面的语义差异仍在 | 可维护旧版，不作为完整重做路线 |
| 独立 V4 空间行为内核 | 同时服务战术、解释与小圆点 | 需要重建协同、规则和校准体系 | 推荐 |
| 高频完整物理模拟 | 视觉空间潜力大 | 开发与校准成本高，当前 2核2GB 目标尚无容量证据 | 暂不采用 |

## 2. 当前源码具备什么，缺少什么

以下以源码为准。旧 docs 中的固定 180 链、随机状态无法恢复、通用比分概率补偿等问题已被后续版本处理，不能再当作现状。主动换人也已经移除。

| 当前证据 | 已具备的能力 | 对新目标的限制 |
| --- | --- | --- |
| `versus/v3/match-engine-v3.js` | V3 入口与参数配置 | 内部仍调用 V2 创建和推进，不是独立内核 |
| `versus/v3/flow-state.js`、`flow-shape.js` | 足球时钟、球权、球区、持球人、转换窗口、连续保存的位置；移动受时间与速度限制 | 权威球状态仍以区域和持球人为主，未形成统一的球飞行、接触、争夺时间线；球员主要向阶段目标位置移动 |
| `versus/v3/action-policy.js` | 少量可行行动、候选价值排序、判断和压力影响决策 | 候选主要依赖区域连接；射门阶段直接返回射门，不是每个触球点统一比较全部可行动作 |
| `versus/v2/possession-chain-v2.js` | 参与者选择、空间因素、能力对比、结果诊断 | `stageProbability` 仍组合阶段基础概率、空间/能力因素及调整项，`attemptStage` 再结算；不少效果还不是具体球路与到达时序的结果 |
| `versus/v3/tactical-execution.js` | 压迫触发、上抢/封线/保护、重点防守、指定出球与过程汇总 | 已有战术行为不是摆设，但还缺完整、持续的无球任务和协同生命周期 |
| `versus/v3/random-state.js`、`match-configuration.js` | 分领域随机状态、配置锁定、检查点恢复 | 应保留这些保证，并为 V4 的进行中行动和同时事件扩展状态模型 |
| `versus/v3/diagnostics.js` | 候选和概率诊断、校准统计 | 详细决策追踪默认受开关控制，且限前 16 条链；不等于全场可查询的解释系统 |
| `versus/v3/key-plays.js` | 实际行动前后位置、只读录制、有限关键回合 | 只保留最多 32 段、每段末尾最多 5 个动作；部分定位球、补射等不支持，不能作为整场时间线 |
| `versus/public/broadcast-key-plays.js` | 客户端插值、关键回合与进球卡 | 射门起点按球区修正，终结球路及部分防守移动为展示推导；新引擎需要自己输出这些事实 |
| `versus/v2/ydl-league-engine-adapter.js` | 比赛推进、加时/点球、报告与公开视图 | 常规直播固定约 120 秒，需拆开比赛推进与个人播放 |

关键判断：现在的位置已影响比赛，但并非所有比赛结果都由可以逐帧观看的具体动作产生。直接把现有关键回合扩为整场动画，会扩大这个差异。

## 3. 战术如何成为比赛的主干

### 3.1 五个阶段与三个决策层级

阶段：有球组织、无球防守、得球转换、失球转换、定位球/重启。现有默认/领先/落后三套预案是这些阶段之上的策略选择，不应混为同一个概念。

决策分为球队、局部小组、个人：

- 球队规定出球方向、宽度、节奏、风险预算、防线位置、留守和压迫触发。
- 小组解决接应三角、边路套插、压迫与保护、盯防交接，限制同一空间被多人重复占用。
- 个人根据可感知信息、职责、身体状态和任务选择行动；不会看到对手未来动作或随机结果。

无球任务至少包括：拉开、回接、前插、套边、内收、支点、保护、盯防、封线、上抢、回撤。每个任务需要启动条件、目标、优先级、持续时间、退出条件和冲突处理，防止所有人每一步改主意或一起追球。

### 3.2 每项战术都要有行为、收益、代价和反馈

| 指令 | 实际行为 | 希望获得的过程收益 | 必须承担的代价 | 可解释指标 |
| --- | --- | --- | --- | --- |
| 左侧组织 | 后腰/边卫提供左侧出球点，附近球员形成接应 | 更多可接球线路、推进人数优势 | 对方压缩左侧后，转移需要时间 | 左侧可接应次数、线路受阻、转移次数 |
| 高位压迫 | 第一人接近持球者，队友封接应和保护身后 | 迫使回传、解围或高位夺回 | 冲刺消耗与被突破后的空当 | 触发/到位/绕过/夺回，额外跑动 |
| 边卫套上 | 边卫择机超越边锋，附近中场补位 | 多一个外线接球点或传中角度 | 失球后需要回追、留守人数下降 | 套上被使用、补位是否到位、暴露走廊 |
| 中锋支点 | 回接、护球、做球，队友围绕第二落点 | 缓解出球压力、连接后续进攻 | 转身慢或第一点被限制 | 接到/护住/回做/二点控制 |
| 低位反击 | 无球保持紧凑，得球时识别前场出口 | 利用对方尚未回收的空间 | 放弃部分高位争夺，出口也可能被封 | 防守入口、夺回位置、出口可用性、推进时间 |
| 耐心组织 | 在机会不佳时保留回传和转移 | 等到更好的接球或射门条件 | 消耗时间，可能错过窗口或丢球 | 等待时间、错失窗口、形成机会质量 |

不再让同一条战术先改善站位，又无归属地额外增加传球/进攻成功率。每个效果必须登记作用层；明确的特性加成可以存在，但需要独立、可追踪的来源。

### 3.3 属性与游戏特性

保留现有属性、强化、国家队/俱乐部羁绊和已批准的球员平衡数据，不在引擎重做中重新计算总评。

重新明确作用位置：视野影响发现机会，决策影响选择，跑位影响启动和目标，传球影响方向/力度误差，停球影响控制和处理时间，速度/加速影响移动，防守能力影响预判与对抗，体能影响可持续执行。

同一个能力可以参与多个有独立含义的机制，但不能把同一影响重复作为通用乘数叠加。卡牌特性、队长、羁绊、伤病免疫等建立兼容表，逐项标记已支持、暂不支持及迁移语义；不默默丢失，也不未经确认删除游戏化规则。

## 4. 新内核建议

建议模块边界：

1. **输入适配与配置锁定**：当前阵容、赛事方案、赛前轮换、球员和特性快照进入不可变 MatchInput。内部实体键使用球队/比赛实体标识加球员实例，兼容双方使用同一球员。
2. **战术编译**：将战术板位置和选项转成阶段结构、任务、触发条件、约束与偏好，并保留配置来源。
3. **感知与决策**：同一时刻双方读取同一份状态，产生意图；分配任务与处理冲突后统一提交，避免先更新的队伍获得顺序优势。
4. **运动与球路**：更新位置、速度、朝向、行动持续时间，以及球的持有/飞行/自由/死球状态。接球、拦截与争顶基于球路和到达时间。
5. **对抗和规则**：在触球、接触、越界、越位、犯规等发生点处理结果；技术误差取样后产生可复现后果。越位在传球瞬间记录判定依据并结合参与行为处理；禁区、球门和边界采用明确几何规则。
6. **事件与解释**：将实际决策和结果记录为结构化事件，并关联战术、参与者和关键因素。
7. **输出适配**：公开帧、个人复盘、管理诊断、统计及赛事结算分别投影；观看不改变引擎状态。

初始原型可试 0.2 个足球秒的固定运动步长，决策以事件触发加低频重评为主。此数值尚未验证，不作为最终承诺。高速球不能只检查步末位置，需计算步内线路相交/到达时间，必要时局部细分。

候选动作要包含接球人和目标点，而不仅是“推进到某区域”。带球、传球、射门都有进行中状态；在合理反应时点允许取消或改意图，不能每帧无代价重新选择。对抗双方同时执行。

空间不保证消除随机性。优先对观察、反应、触球和技术误差建模；即使保留概率式对抗，也应在明确接触条件下判定，而非画面已穿过封堵者后再解释为区域成功。

## 5. 可解释性是引擎输出协议

解释至少分四层：

- **意图**：哪套方案、哪条指令让球员承担什么任务。
- **条件**：接球窗口、封线、可达时间、队友支援、疲劳等当时事实。
- **选择**：有哪些可行选项，为何选中当前动作，哪些被排除。
- **结果**：实际发生了什么，技术执行与防守响应怎样改变状态。

示例仅用于说明表达结构，并非现有比赛测得的数据：

> 左侧组织触发 → 后腰回接形成出球点 → 对方前锋封住向前线路 → 中卫选择横传 → 对方压迫转向，右侧出现推进机会。

另一种失败应明确为“边卫尚未到接球位置，指令未能执行”，而非统一显示“战术无效”。也应区分执行后被对方识破、判断次优和技术失误。

建议事件保留：事件序号、足球时间、状态版本、参与者、动作、指令来源、候选摘要、选中理由、实际对抗、结果、关联前后状态。完整候选表和随机信息仅诊断模式记录；常规比赛保留紧凑摘要与关键片段证据，设置容量与保留期。

界面分层：实时一句话；点击事件看路线/职责/压力；赛后看触发机会数、执行率、受阻类型、收益及代价。不能只报告“成功多少次”而忽略本来有多少次可执行机会。

解释中的评分差不等于因果贡献百分比。不能宣称“某条战术贡献了这粒进球的 37%”。单次选择的解释是程序实际依据；“换成另一战术是否更好”需要冻结场景与多种子对照，且轨迹分叉后相同种子也不等于逐事件随机条件相同。

公开观看只展示可见行为；本队复盘可展示自身指令；对手未公开战术、完整决策候选和随机状态不通过直播接口泄露。

## 6. 为可调速小圆点直播预留的协议

### 三个时间轴

- **足球时间**：引擎的权威比赛时间。
- **服务器推进/发布进度**：后台已经计算并允许对外发布到哪里。
- **个人播放进度**：观众正在看到哪里。

调速与慢放只改变个人播放进度。观众慢放不暂停赛事、赔率截止或其他观众；可以落后于直播并一键追上。比分、文字、统计和事件卡必须跟随同一播放游标，不能在回看进攻时提前显示后面的进球。

已计算但未到公共发布时间的结果不能通过比分、帧、统计、回执或其他API提前泄露。领先公共进度时等待，不能由客户端自行推演未发生的比赛。

若仍将 90 分钟压成约 120 秒，平均为 45 倍足球时间：战术跑动很难持续辨认。建议普通推进快放、关键阶段按足球秒尺度慢放；完整观看允许更长时间，赛事服务端结束不强制观众立刻结束回看。具体默认时长、慢放倍率与片段触发阈值待原型体验决定。

### 最小播放数据

- 头信息：协议/引擎版本、比赛标识、场地尺寸、坐标约定、阵容身份、半场攻向。
- 按时间排序的关键帧/增量：球员位置、速度或受约束路径、行动状态、球的位置/高度/运动段、比分和规则状态。
- 动作事件：起止时间、传球出脚、接触、拦截、射门、死球等关键时间点；事件与帧共享序号关系。
- 获取协议：按游标取数据、序号去重、基准关键帧、缺帧补取、断线重连、完整性校验。

引擎使用明确的世界坐标和攻向；战术板的 0–100 坐标只在适配层转换，半场换边不靠到处翻转局部坐标。球员可用米制二维坐标，球使用轻量高度模型。

客户端可以插值和平滑镜头，但不能改写接触点、射门起点、成功接球或进球。插值必须经过引擎记录的关键接触点，不能为了平滑越过抢断、边线或死球边界。

采样、网络发送、浏览器渲染是三个不同频率：浏览器可按显示刷新率渲染，不要求服务器逐帧发送或写盘。优先记录可还原的运动段、事件和稀疏关键帧；复杂片段自适应加密。具体压缩方式和传输机制待数据量实测选择。

即使正式小圆点页面后做，V4 第一阶段就必须有开发用简易球场播放器。仅看文本日志很难发现瞬移、重叠、全员追球和封线不成立的问题。

## 7. 性能与持久化约束

固定目标仍为阿里云香港 2核/2GB/64GB、10人在线。此前收件箱与预测压测未包含新引擎同时比赛，不能用于证明 V4 可承载。

规模估算，忽略补时/加时：0.2 足球秒一步，90分钟约 27,000 步。若仍在120现实秒内推进完，为每场约225步/现实秒；8场同时约1,800步/现实秒。这里只是步数，不包含决策、空间查询、持久化和网络成本，更不是运行性能预测。

建议：

- 比赛计算在有界后台工作线程中执行；比赛状态由单一执行方拥有，主线程负责服务、调度和提交，不为每名观众重复模拟。
- 2核机器优先验证少量 Worker 复用与限额调度，不能一场一个 Worker 无上限竞争；正式比赛、训练和预测分别设优先级与预算。
- 快速/离线模拟和观看模拟使用同一内核与规则；关闭录制只减少输出成本，不能改结果。
- 使用局部查询、空间索引、缓存稳定战术编译结果，减少逐步全队全量重建与对象复制。
- 比赛轨迹与账号/资产存档分离。资产仍原子结算；轨迹按块追加、检查点按版本提交，不把所有帧塞回现有同步联赛 JSON。
- 检查点保存进行中行动、球的飞行状态、任务、待处理事件、随机状态、序号及锁定配置；恢复后可以重算尚未发布部分，但不得重复结算或改写已提交历史。

验收分别测 1场、8场以及调度可能出现的赛事重叠压力档，叠加10人浏览、开包/收件箱、后台预测；报告计算CPU、调度积压、HTTP P95/最大值、内存、落盘和网络量。比赛容量与观众容量分别统计。

可先将单次调度工作控制在约5–10ms、关键HTTP P95不高于100ms作为待验证工程预算，不能视作当前保证；最大延迟、工作线程滞后和长期内存增长也必须有边界。最终阈值以原型测量和香港实机验收确定，不能只拿平均值通过。

## 8. 兼容与迁移

- 复用账号、卡牌资产、抽包、交易、奖励、联赛/杯赛赛程及结算框架，增加版本化 MatchInput/MatchResult 适配器。
- 保留赛前轮换、赛事方案绑定、默认/领先/落后站位跟随。战术字段建立旧→新语义清单，不直接照搬旧加成数值，也不静默忽略。
- 玩家与AI执行同一比赛规则；AI继续用23人名单及双方案决策。
- 比赛内仍只支持伤退、门将红牌等被动处理；名单、5次名额、低体能限制和应急门将规则需适配V4状态，不直接搬旧状态修改函数。
- 历史比赛保留旧引擎、旧配置和旧报告；进行中的比赛不切内核。优先按赛季边界切换，并为赛季、比赛及报告记录版本。
- 新旧版本并行影子模拟只用于评估，不重复发奖，也不要求两个内核逐场同比分。比较的是规律、战术效应、强弱关系与异常分布。
- 球员数据保持不变不代表平衡自然不变。新决策和移动模型会改变不同属性、职责和阵型的实际价值，需要重新验证，不能未经用户确认回改已批准球员属性。
- 预测当前明确使用V1、24样本和原赔率规则；此次评估不改动。V4上线前须单独评估预测与实赛模型偏差，决定继续旧模型还是另行授权版本升级。无论选择哪条路径，已投注赔率和原有结算契约必须保留，不能在本轮顺带切换。

建议首个决策点设在阶段1结束：能否从同一段权威状态同时看懂位置、战术选择与结果，且计算成本可控。达不到时先修空间/任务模型，不提前投入完整直播美术。

## 10. 验证体系

1. **确定性与一致性**：连续运行、任意检查点恢复、不同推进批次、录制开关、不同播放倍率得到相同事件和结算；保存规则与版本，明确支持的运行时范围。
2. **空间和规则不变量**：持球归属唯一；飞行球可无持球者；接触必须时空可达；不可越界持球；普通红牌不补回人数；无非规则重启瞬移；同时事件有稳定优先级。
3. **局部战术场景**：二打一、封锁后腰、弱侧转移、边卫套上后失球、门将出击、压迫被绕过等，检查具体行为与解释，不依赖最终比分。
4. **整场对照**：相同真实阵容、多个种子、主客互换，分别观察推进、线路、射门质量、失球位置、压迫到位、体能代价，再看胜率和进球分布；报告样本和不确定性。
5. **执行校准**：按距离、压力、能力与对抗类型检查传接/射门等概率或误差分布。区分机会质量与包含射手/门将后的进球概率，避免用一个xG值解释所有能力因素。
6. **对抗性场景**：无限回传耗时、连续无效压迫、满员挤禁区、极端站位、重复球员ID、低体能、连续红牌伤退、比赛结束/点球边界。
7. **播放与运维**：低速网络、重连、迟到观众、慢放后追赶、比分不剧透、进程崩溃恢复、磁盘失败、轨迹缺块、重复结算拦截。
