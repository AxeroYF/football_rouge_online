# 游戏体验、冗余加载与多人内存审计（2026-09-20）

## 结论与范围

本轮是系统性评估，未修改游戏逻辑、未生成新热更新包、未部署服务器。代码基线为本地 R29；用户最后确认服务器已部署 R28，不能把 R29 当作线上已生效。覆盖主状态同步、地图、移动、编队/卡片、开包、建筑/研究、商店、通知、外交/交易、联军、豪门活动、比赛与持久化链路。

主要问题不是正常操作频繁刷新整个网页，而是“完整状态轮询 → 多模块处理 → 打开的窗口再次请求详情”，以及服务端长期记录累积后被事务快照和整库保存放大。尚未复现线上 OOM；已确认若干记录缺少保留边界，属于需要优先治理的长期风险。

证据等级：**确认**为源码路径直接支持；**本地实测**仅代表本机隔离样本；**待验证**不能作为已发生的问题。本文代码路径均相对仓库根目录，行号对应审计时版本。

## 按 P 等级排序

P0：优先消除无界增长、建立监测，不代表已发生线上故障。P1：影响高频操作和多人负载，紧随其后。P2：局部增量优化。P3：低收益或正常必要行为。

## 多人内存与持久化边界

### 已确认的增长路径

1. `diplomacy.status()` 只计算 expired，不等于删除申请；详情中的 slice 只限制返回数量，不能限制持久化字典。
2. 友谊赛完成后写入 battle，但未去除 match.leg；matches 历史继续驻留。之后 transaction 对整个 diplomacy 做克隆，又会复制这些历史。
3. 回执追加位置：`airport-service.mjs:38`、`coalition-service.mjs:260`、`elite-raid-service.mjs:167`、`building-service.mjs:360`、`elite-challenge-service.mjs:40`，外交 read 回执在 `diplomacy-service.mjs:189`。这些路径未发现对应正常运行时保留上限。
4. `server/infrastructure/json-campaign-repository.mjs:15,23–43` 启动时全文件解析，保存时整个 accounts/world 序列化并同步写入、fsync、rename。数据越大，字符串/编码缓冲和回滚快照越容易同时占用内存，并阻塞请求处理。
5. `diplomacy-service.mjs:37–40` 的事务快照、联军非快速操作的广域快照、精英比赛事务的活跃比赛克隆，是瞬时放大器。R29 交易报价与中止快速路径只优化了部分操作，不能推定全站已无全量快照。

### 已有保护与不可误判项

- 部署模板 `deploy/aliyun/yellowdogs-rougelite.service:11,22–23` 为 old-space 768 MB、MemoryHigh 1100M、MemoryMax 1400M。不是实际线上配置证明，也不意味着整个 Node RSS 只有 768 MB。
- 静态压缩缓存 `server/http/static-asset-cache.mjs` 默认约 16 MiB，有 LRU、单文件大小上限、压缩并发上限及同文件请求合并。存在并发临时缓冲，但不是当前首要无界对象。
- 战报、强化历史、世界事件、部分联军记录与合卡回执已有不同保留策略。仍要测单条大小，但不能全部归为“无限增长”。
- 地图空间缓存已有数量边界；迷雾预览有过期检查。需按实际对象存活链分析，不能因为出现 Map/WeakMap 就判泄漏。
- nginx 模板目前发现的请求限速主要针对登录；业务端点还需结合正常客户端峰值设计并发预算。先去掉重复请求，再做端点级保护，避免一刀切误伤正常玩家或同一网络的多人。

### 安全的清理设计

终态回执至少保留明确的重试窗口；过期请求须通过时间/版本协议拒绝，或保留有界去重水位，不能简单删除 receipt 后再次执行原请求。金融/交易待处理项、未领取奖励、活动比赛不能按普通缓存 TTL 删除。先清理已结束比赛运行态与可安全截断的历史，旧存档迁移分批处理，保留备份并验证重启后幂等性。

首次目标是让每类记录有可解释的保留界限，以及在固定账号数、持续操作下不随操作总次数无限增长。不要为解决内存而牺牲已确认交易的持久化、失败回滚或战报入口。

60 个模拟账号条件下增加 5 场精英比赛，推进 150 个调度切片后，存档约 6.64 MiB，单次 save 122.05 ms；比赛仍在约第 10 分钟，不是完整比赛/长期运行结果。调度切片平均 23.42 ms、P95 42.55 ms。

这些数据支持“整库保存和比赛对象增长值得优先优化”，不支持“已经证明没有 OOM”。显式 GC 的采样看不见全部瞬时峰值；没有历史的 33 张卡账号严重低估长期真实存档。更弱服务器上的耗时可能更大，不能简单按 CPU 型号换算。

## 建议落地顺序和验收

1. **第一批：稳定性与小改动。** 内存/记录数量低频监测，已结束比赛运行态清理，安全有界回执方案；补互动/豪门请求在途锁、关闭竞态与错误退避。改动集中，可独立回归。
2. **第二批：状态与加载。** 分区版本+增量响应；建筑详情按依赖版本拉取；统一在途状态请求；客户端订阅选择器和地图更新合并。这一批预计最能改善普遍卡顿与服务器重复计算，收益需前后对照量测。
3. **第三批：大存档与大仓库。** 缩小事务快照，比赛详情存储与读取分离，大仓库渲染优化。若存档保存仍占用显著事件循环时间，再评估数据库/日志式持久化，避免一次重构太大。

验收指标（目标，不是本轮已达成）：

- 页面可见且无操作、世界无变化时，除轻量 heartbeat 外，不重复下载仓库/建筑目录/历史；闲置响应字节相对当前样本下降至少 70%，通过 Network 统计验证。
- 每个功能键至多一个在途请求；人为延迟响应 10 秒、反复开关窗口/切账号后无后台 timer 复活、无旧账号数据回填。
- 建筑/强化详情不因无关世界变化重拉；关键依赖变化、结算、借调、交易后仍及时刷新。
- 地图同一轮状态更新只提交一次相关图层刷新；保持拖动、输入焦点、仓库滚动和战术板拖拽，不出现全窗口闪烁。
- 对每一类回执、申请和历史运行超过保留数量的模拟操作，验证记录数有界；重试不会重复扣费/发奖，重启后仍成立。
- 使用 200/1000 张卡、满历史、不同累计账号数与活跃比赛数，在接近目标服务器配置下做至少 30–60 分钟稳态测试；记录 RSS/heap 趋势、请求与保存 P95/P99、事件循环延迟。停止负载后观测内存是否趋稳。
- 迁移前备份、迁移后重启、保存失败回滚和磁盘不足路径均需验证。未取得实际服务器 RAM、进程 RSS、存档大小及活跃人数前，不给出可靠人数上限或“保证不 OOM”的承诺。

本轮只新增审计文档与隔离基准脚本/结果；游戏实现需按上述顺序另行落地与回归。
