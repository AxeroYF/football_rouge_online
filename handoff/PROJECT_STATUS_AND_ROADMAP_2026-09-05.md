# Rougelite 项目状态与开发路线图

更新时间：2026-09-05

## 本次交接范围

本文件补充当前项目完成度判断、10 人好友服部署结论，以及后续开发路线。旧 handoff 文件继续保留，用于追溯已经完成的具体实现。

## 最新产品决策

- 项目定位为约 10 名朋友共同游玩的私人服务器，暂不按大规模公开运营设计。
- 继续使用 Three.js，不更换渲染引擎。
- 安卓客户端优先采用 Capacitor 封装现有 Web 前端。
- 服务器使用一台小型云服务器即可：Caddy/Nginx + 单个 Node 进程 + 现有 JSON 存档 + 自动备份。
- 暂不引入 PostgreSQL、Redis、负载均衡等复杂基础设施；只有玩家规模或并发明显扩大后再迁移。
- 频繁开发阶段可让客户端加载服务器上的前端，以便界面和规则更新后立即生效；安卓外壳变化时再发新版 APK。
- APK 必须长期使用同一签名密钥。
- 设施扩展暂缓，近期重心转向球员管理、强化、阵容、比赛和完整玩法循环。

## 当前最高优先级

下一阶段首先建立唯一的“球员最终属性计算入口”。基础能力、训练成长、强化等级、强化特性和比赛临时状态必须在同一处计算，并由以下界面和服务共同使用：

- 球员卡与 26 项能力面板。
- 背包和球队列表。
- 战术板磁贴与悬浮信息。
- 同名球员最佳实例选择。
- AI 自动选人和比赛引擎。
- 比赛报告和历史记录。

需要重点回归强化特性 `996`：体力固定为 94 时，卡片、能力面板、战术板和比赛引擎必须都得到 94，不能被训练值或其他强化逻辑再次覆盖。

同名球员选择顺序暂按以下规则统一：

1. 强化等级最高。
2. 综合训练提升最高。
3. 最终综合能力最高。
4. 使用稳定的实例 ID 或获得时间打破平局。

训练中、远征首发、留守首发只是状态标记。强化成功或失败不应破坏阵型、远征队槽位和训练任务引用。

## 开发路线

### 阶段 0：核心数据收口与稳定性（1～2 周）

- 完成最终属性统一计算与比赛引擎回归。
- 回归战术板落位预览、强化等级、特性显示和同名球员筛选。
- 验证强化主卡/副卡选择、仓库隐藏、结果卡暂存和强化记录。
- 所有长期任务以服务端结束时间为准，服务器重启后可恢复训练、球探和移动状态。
- 增加存档版本号、迁移、定时备份和测试账号重置工具。
- 建立至少一条完整流程测试：获得球员 -> 强化/训练 -> 编入阵容 -> 完成比赛 -> 保存并重启恢复。

验收条件：不需要手工改存档即可完成一次完整循环，服务重启不会重复结算或丢失任务。

### 阶段 1：单人发展闭环（2～3 周）

- 建立金币来源与消耗表。
- 地块提供基础收入、首次占领奖励和轻量持续收益。
- 增加每日、每周任务。
- 开发第一个地区 PVE 联赛或杯赛。
- 增加 AI 难度梯度、首次通关奖励和比赛报告。
- 球员收藏增加同名分组、收藏、锁定、批量筛选和“可强化”入口。

目标循环：PVE/地块事件 -> 金币与卡包 -> 球探/开包 -> 球员管理 -> 训练/强化 -> 阵容与战术 -> 新比赛。

### 阶段 2：异步 PVP（约 3 周）

- 玩家保存防守阵容，其他玩家可异步挑战。
- 服务端完成比赛并生成关键事件、评分和结果记录。
- 增加每日挑战次数、复仇入口和防刷奖励规则。
- 增加周积分榜、好友排行榜和主客场。
- 建立 10 人周联赛以及月度杯赛。

PVP 奖励以荣誉、外观和少量资源为主，避免领先玩家依靠胜利奖励继续扩大硬实力差距。

### 阶段 3：地图争夺与 PVE 深度（2～3 周）

- 地块增加资源倾向：商业、训练、球探、主场或交通。
- AI 势力占据关键地区，形成区域征服目标。
- 攻击前准备时间、战败保护和首都进攻路径规则。
- 远征移动、补给与连续作战状态。
- 周期性世界事件和国家球探概率活动。
- 天气和地形只提供轻量战术影响，避免随机因素直接决定胜负。

### 阶段 4：社交、赛季和安卓好友版（2～3 周）

- 比赛邀请、结果动态流、预设表情/留言和球员卡分享。
- 玩家之间有限场次的球员租借。
- 管理员创建杯赛、世界事件和奖励。
- 4 周小赛季：地图占领与排行榜重置，球员收藏、训练和强化保留。
- 部署 HTTPS 好友服务器。
- Capacitor 横屏 APK、返回键、沉浸式显示、版本检查和 APK 更新入口。

## 推荐的新玩法

近期高价值功能：

- 地区 PVE 联赛和杯赛。
- 异步玩家挑战与比赛回放。
- 周联赛、月度杯赛和赛季荣誉墙。
- 同名球员分组管理和完整球员生涯记录。
- 管理员赛事工具，用于十人好友服快速组织活动。

后续设施候选：

- 数据分析中心：赛前查看对手倾向、可能阵型和薄弱区域。
- 青训学院：长周期培养偏向当地国家的低等级球员。
- 医疗中心：主动安排恢复，降低伤病影响。
- 商业中心：在赞助、门票和商品收入之间选择经营方向。
- 交通枢纽：缩短远征移动时间。

暂缓项目：

- 实时在线 PVP。
- 自由拍卖行。
- 复杂联盟战争。
- 完整实时聊天。
- 大量只有百分比加成的设施。
- 新增多套养成货币。

## 10 人好友服部署结论

- 一台 2 核、2～4 GB 内存、40 GB 以上 SSD 的云服务器足够起步。
- 使用 Caddy 或 Nginx 提供 HTTPS、缓存和反向代理。
- 只运行一个 Node 进程，避免多个进程重复执行定时任务或同时写 JSON。
- 游戏资源初期可直接由同一服务器提供；下载速度不足时再迁移地形和球员资源到对象存储/CDN。
- 每小时保存短期备份，每日保存长期备份，保留至少 7～14 天。
- Node 服务异常自动重启，停止前执行最后一次存档。
- 移除管理后台默认密码并限制管理接口访问。
- 玩家规模不扩大时无需 PostgreSQL、Redis 和多实例部署。

## 协作与运行约定

- Codex 不替用户启动或停止 4370 开发服务，服务启停继续由用户负责。
- 修改持久化存档前应先停服，避免旧进程覆盖新数据。
- UI 修改后优先运行静态/单元测试；需要浏览器验收时由用户启动服务并执行最终视觉检查。
- 保留现有地形方案和旧入口时，应继续遵循当前产品决定，不主动更换 Three.js。
