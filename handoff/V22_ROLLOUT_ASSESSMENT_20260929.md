# V2.2 与 V2.1 对比及灰度接入评估

日期：2026-09-29。评估基于当前本地代码与公开示例阵容。未修改正式比赛引擎入口、线上配置或经济结算，未打包部署。

## 本次 Demo 调整

- V2.2 常规比赛从 600 秒改为 360 秒，映射 0–90 分钟；淘汰赛常规战平后再模拟 120 秒，映射 90–120 分钟，共 8 分钟。联赛/普通赛战平直接结束。加时不采用金球制。
- 运动仍是固定 20Hz，速度和加速度不随时钟倍率增加。展示时钟现为 15 倍，跑位目标继续 2Hz。
- 独立浏览器 Demo 使用淘汰赛示例以便观察加时。加时仍平局标记 `needsPenalties`，当前不模拟点球大战，也不凭随机硬判赢家。正式双回合总比分判定尚需适配。
- 射门由距离、可见球门角度、封堵路线、实际角色和战术细节决定。中路清晰机会优先起脚；前锋的正常射程略扩展，但尊重减少远射。前方有空间时不再因传球计时到期而被迫回传；受压、通道被封堵时仍允许回传。
- 34 项测试通过，覆盖清晰机会起脚、被封堵时释放球权、窄角度不盲射、六分钟结束、平局加时、VAR 先判定再决定加时等。

同种子 A/B：12 组公开阵容，双方都使用 360 秒；对照版本仅恢复本次调整前的射门/回传选择。统计对象为进入前场 65m 后的 ST/LW/RW/AM 普通传球，向后超过 3m 记为回传，不含传中。回传从 35/387（9.0%）降至 9/356（2.5%），每场双方射门合计均值从 9.67 增至 10.08。样本用于验证方向，不是平衡性验收，也不代表每一场都会射门更多。

## 两套系统的核心区别

| 维度 | V2.1 正式系统 | V2.2 当前原型 |
| --- | --- | --- |
| 比赛推进 | 控球链、区域、能力与战术概率，正式常规赛 180 回合 | 22 名球员与球连续运动，7200 个固定步长完成常规赛 |
| 战术执行 | 回合数值、空间模型与职责修正影响结果 | 复用 V2.1 参数和角色，再形成实际套边、内切、接应、封堵和球路 |
| 结果来源 | 服务端权威 V2.1 | 空间过程独立产生比分；同阵容同种子不保证与 V2.1 相同 |
| 数据兼容 | 正式账号、独立联赛名单、体力、特性、天气等 | 能接收相同席位、强化后的属性、站位/职责/预案，尚非完整功能等价 |
| 规则与特性 | 已接通红黄牌、伤停、换人、加时点球、天气与赛后影响等 | 空间越位、进球 VAR、边界归属、传接抢射和加时；完整犯规/头球/特性事件等不齐全 |
| 时长 | 正式常规每回合约 120 秒，加时约 40 秒 | 常规 360 秒，加时 120 秒，独立 Demo 配置 |
| 持久化 | RNG 状态、恢复、赛后影响幂等与归档已有正式调用链 | RNG 为闭包、有效球员为 Map、事件仅保留尾部 100 条，缺少正式检查点与恢复协议 |
| 客户端 | 轮询已确认比赛状态 | 本地模拟与 Canvas 插值；目前只是公开数据 Demo |

V2.2 的优势是战术可观察性与空间因果，现阶段主要障碍是功能完整性、可恢复性和结算契约，不是球员能否流畅移动。

## 本机成本实测及边界

环境：i7-12700K / Node 22.17.1，公开阵容两队各 11 人，无真实账号。每模式 2 次预热；旧版对比各 8 次，新六分钟版本 12 次。统计构建加完整推演耗时，不含渲染、网络、存档和生产服务混合负载。

| 模式 | 完整计算耗时中位数 | 样本最大值 |
| --- | ---: | ---: |
| V2.1，180 回合，现行默认不生成 dot replay | 5177ms | 5379ms |
| V2.1，额外开启 dot replay | 5142ms | 5325ms |
| V2.2，上一次 600 秒版本 | 377ms | 423ms |
| V2.2，本次 360 秒版本 | 234ms | 263ms |

V2.1 的 replay 耗时小幅更低是抽样波动，不是加功能更快；8 组相同种子比分一致，仅证明这些样本没有比分变化，不能替代全部事件/结算回归。当前 V2.2 缺少完整正式能力，两者不是功能等价的性能比较，不能据此承诺上线后节省多少 CPU 或可承载多少用户。

样本 V2.1 最终公开状态约 144KB JSON / 15KB gzip，开启旧回放后额外帧约 337KB JSON；V2.2 原型初始化输入约 48KB JSON / 6KB gzip。这些是样本数据体积，非正式协议预算；当前 V2.1 公开响应也没有直接提供 dot replay 帧。

正式系统当前每 100ms 调度，按服务轮转推进有限比赛回合，统一存档计时默认 5 秒；联赛同时最多 5 场，联赛推进检查点约 30 秒。转播通用轮询间隔 1 秒。把“整场计算 5 秒”理解为现有接口每次堵塞 5 秒是不准确的；正式服务已拆成回合。真正要关注的是高峰各类比赛合计的主线程时间、重复构造公开状态、存档和响应体成本。

基准原始数据：`outputs/v22-demo-review/rollout-benchmark.json`。没有取得当前生产机规格/高峰数据，不能直接把本机数字折算成线上容量。

## 推荐灰度路径

### 第一阶段：V2.1 结算，赛后动态回放小范围开放

最先接入“查看动态回放”，以现有战报为唯一事实来源。服务端输出带序号的关键事件、当时首发/换人/职责/阵型快照、球权及传球/射门参与人；客户端复用 V2.2 跑位和绘制能力，在事件约束下生成过渡动作。

这里必须新增受事件约束的回放驱动器，不能让当前 `V22HybridMatch` 独立跑出另一套比赛，再只覆盖最终比分。进球、进球者、红牌、伤停、换人、比赛终止及比分变化必须与 V2.1 完全一致；缺少细节时做明确镜头切换，不伪造相反的球路或判罚证据。

首批只开放完整、可表达的赛后片段，遇到暂不支持的事件回到原有转播。这一阶段的 VAR 可显示服务器确认的结论，不能用动画合成位置重新推翻 V2.1 结果。

现有正式比赛 2 分钟而回放 6 分钟，先做赛后播放能避免直播时钟冲突。若要六分钟实时比赛，应作为后续新的比赛时间配置随比赛创建固化，不能只把客户端进度条放慢。已结束比赛可暂停/快进，不能拖延正式结果和奖励到账。

### 第二阶段：独立试验赛验证 V2.2 的结果

新增无排名、无资源和体力影响的测试比赛，或先离线对真实结构的脱敏快照进行影子计算。影子比赛不产生第二次结算，不默认对全服所有比赛双跑。先覆盖多阵容、职责、强化极端值和高低体力，比较胜率、射门、进球、回传、越位和特殊事件分布；两引擎不要求逐场同比分。

展示灰度可按账号白名单或稳定散列 5% → 20% → 50% → 100%，并允许主动退回旧观赛。权威引擎灰度必须按比赛 ID 固定分组，双方只能共享同一版本，不能按各自账号分别决定算法。

### 第三阶段：满足前置条件后，少量正式比赛采用 V2.2

优先开放符合支持范围的普通友谊赛，后续再扩大到地块单场、联赛、双回合及淘汰赛。正式友谊赛是否计体力/伤停必须遵守当前玩法，不能借“友谊赛”跳过结算接入。每日联赛涉及积分、射手、收入、独立体力和伤停，建议最后开放；公平性需要时整轮或整赛日固定算法。

必须完成：
1. 定义权威结果 DTO：个人进球/助攻/评分、实际出场、体力变化、伤停禁赛、换人、弃赛、加时、点球与总比分。当前 V2.2 只有简化队级统计不能直接喂给联赛结算。
2. 支持可恢复 RNG、固定 tick、当前球路、延迟越位/VAR、球员状态和预案的完整检查点；验证重启和中断恢复与不中断结果一致。
3. 正式场次完整事件流按序增量保存，不依赖 Demo 的 100 条尾部日志。冻结开赛输入，球员后续强化/出售不能反向更改已开赛数据。
4. 允许必要的少人比赛状态；目前输入严格要求 11 人，尚不能覆盖红牌后的完整流程。
5. 保持联赛条件写回独立 `leagueRegistration.conditions`，不能污染远征/留守体力；延用幂等结算事务，重复 worker 回传也只能结算一次。
6. 固化 `engineVersion / rulesVersion / renderVersion / seed / inputHash / duration / extraTimeDuration`。正式双回合由总比分触发加时，点球必须完整接入。

## 低配服务器设计约束

- **每场只计算一次。** 权威结果服务端产生，客户端计算只服务画面；不接受客户端上传的比分/奖励。观众增加只增加数据分发，不增加比赛模拟实例。
- **阶段一尽量不新增动态服务器模拟。** 比赛公共事件按 `(matchId, revision)` 缓存复用；鉴权和个人观众信息另行处理。增量读取用 `afterSeq`、序号去重和断线续传；避免每次轮询重新复制全队全战报。
- **客户端负责 20Hz 跑位和 30/60FPS 插值。** 只有打开的一个观赛窗口工作，低配设备降绘制帧率，后台暂停绘制；直播重新进入时按服务器序号恢复，不补跑后台全部渲染帧。
- **不传 20Hz 全员坐标流，不写逐帧存档。** 服务端提供关键事件和低频纠偏锚点；关键事件及时发送，普通变化可 1–2 秒合并。赛后压缩回放作为独立可过期归档，不塞进每次全局存档。
- **完整权威 V2.2 放有界任务池。** 真正接管比分后，建议先设全局 1 个计算 worker，按实际 CPU/RSS 和队列耗时决定是否增加；不要每场、每位观众创建线程。worker 隔离事件循环但不会凭空减少总 CPU，低内存机必须实测加载额外引擎的常驻开销。
- **实时比赛分段推进并限额。** 例如小时间片推进、每段设置墙钟预算、保存可恢复检查点；积压时拒绝新增试验场次或推迟开始，不能静默丢 tick、降裁判精度或更改已开始的算法。
- **禁止提前泄露可推导结果的数据。** 独立模拟的完整种子和双方全部输入若提前交给客户端，可以本地快算出结局；直播仅释放当前允许观看的事件/状态和视觉种子，赛后再发完整可复现包。隐藏的对方预案不应随公共包泄露。
- **两类开关分别回退。** `dynamicReplay` 可立即回到旧画面；`v22Authoritative` 关闭后只影响新建比赛。已开赛 V2.2 应按原版本恢复/完成，不能故障时用 V2.1 重赛并替换已公开结果。

## 进入下一批灰度的检查项

先记录目标机当前高峰基线。建议以以下初始门槛试运行，再按实际机器调整；这些是建议，不是已通过的生产验收：

- 任意比分/事件矛盾、重复奖励、体力串账、重启丢场：停止扩大，关闭对应新入口。
- p95 事件循环延迟、关键接口响应和比赛推进积压不明显劣于基线；可先以 p95 延迟 50ms、API p95 增幅 20% 作为预警起点，不满足时先调查现有基线。
- 高峰保留约 30% CPU 余量，RSS 在机器实测安全预算内，无持续增长；不把 worker 增加当作自动扩容方案。
- 移动端 30FPS 目标、后台恢复、断网重连、同场多人观看、归档清理和旧客户端兼容均通过。
- 通过混合压力测试：联赛五场并行叠加现有挑战/友谊赛及多观众，不只测单场纯引擎耗时。

建议下一次实施范围是第一阶段的“权威事件适配 + 受约束动态回放 + 白名单开关 + 共享缓存/增量传输”。先保住现有结算和低配稳定性，再决定是否值得完整替换权威引擎。

## 关键代码入口

- `engine/campaign-match-engine.mjs`：正式比赛创建、推进、恢复与公开转播。
- `server/scheduler/challenge-scheduler.mjs`：100ms 调度与存档间隔。
- `server/application/daily-league-service.mjs`：并发上限、独立联赛条件、统计和结算。
- `server/application/match-consequences.mjs`：伤停影响及幂等标记。
- `server/infrastructure/runtime-observer.mjs`：已有事件循环、内存和存档监控，可扩展按引擎统计的计算量/队列/回放指标。
- `campaign-broadcast.js`：现有转播客户端与轮询。
- `engine/s4-v2.1/versus/v2/dot-replay-v2.js`：已有关键帧生成能力，需协议裁剪和严格结果不变回归，不能直接当逐帧直播流。
- `engine/v2.2/`：新原型与输入适配；`attacking-decisions.js` 是本次射门/推进选择。
