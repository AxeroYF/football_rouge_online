# R11 访问故障排查 · 2026-09-19

## 当前结论

优先排查公网入口/Cloudflare 访问链路，同时修复游戏入口的容错缺口。不能把本次问题统一归因为游戏性能，也不能仅凭本机实验宣布正式服根因已完全确认。

用户确认正式服已安装 R11，最初停服，随后于本次排查中重新开服并授权访问 https://yellowdogsleague.online/versus/ 。用户报告登录后地图不进入与网页本身打不开两种现象；手机能进入、电脑不能进入。尚未确认两端是否同一账号、同一 Wi-Fi、同一时刻。

所有命令通过本地 PowerShell 7.6.5 执行。没有登录真实账号、修改正式服、重置存档、部署代码或对正式服压测。仅少量公开 GET/HEAD 请求。容量测试与故障注入使用本机隔离账号。

## 1. 正式公网访问：已复现连接阶段失败

北京时间约 17:22–17:28，从本机观察：

- DNS 返回两个 IPv4：104.21.41.59、172.67.189.119，以及两个 IPv6；成功响应的 Server 为 cloudflare。
- 全新桌面 Chrome 首页导航超时，记录 net::ERR_TIMED_OUT，未收到首页 HTTP 响应。手机模拟视口在同一台电脑和网络上也失败；它不代表用户真实手机网络。
- PowerShell Invoke-WebRequest 分别发生 20 秒超时与 TLS 连接失败；curl 随后得到过首页 200。
- 对两个 DNS 返回地址做保留 Host/SNI 和 TLS 校验的只读对照：104.21.41.59 在三轮中全部于约 5 秒连接超时，未完成 TCP/TLS；此前额外一次约 6 秒超时。
- 172.67.189.119 三轮分别为：TLS 已完成但 10 秒未收到数据；200 / 6.30 秒；200 / 1.23 秒。此前还成功取得健康接口 200 / 2.30 秒。
- 通过 172.67.189.119 获取 /versus/ 成功：200，1.73 秒，67009 字节。HTML 中 app、campaign-entry 和 map-loading-recovery 的版本标识与当前 R11 源码一致。这只核对公开入口，不等于校验全部服务器文件。
- 独立 Chrome 指定 172.67.189.119 后仍出现导航超时。因此不能承诺简单固定某个 IP 就能解决。
- 交接中的源站 8.210.0.104 TCP 约 65ms 建连，但直接 HTTPS 证书链不被本机信任，未取得应用健康响应。没有关闭证书校验。CDN 源站证书可能采用专用信任体系，此现象不能单独判为配置错误，也不能据此证明源站应用健康。

**判断边界：** TCP/TLS 之前的失败不能由地图渲染或游戏状态计算解释，证实本机到公网入口存在问题。172 地址完成 TLS 后等待响应的超时，仍可能涉及网络、CDN 到源站或源站应用，需要日志区分。尚不能断言 Cloudflare 全局故障、全部玩家同因、DNS 一定配置错误、WAF 封禁或服务器 OOM。

## 2. R11 入口容错：已用故障注入复现

| 本地隔离场景 | 结果 |
| --- | --- |
| 正常桌面 Chrome，无忽略 GPU 黑名单等参数 | 地图约 6.66 秒就绪，无页面异常 |
| 手机模拟视口，相同电脑网络 | 约 5.92 秒就绪，无页面异常 |
| 已有登录令牌，首个 /api/campaign/state 永不返回 | 等待 28 秒，入口为空，无登录框、无恢复按钮 |
| campaign-api-client.js 下载失败 | 等待 28 秒，入口为空，无登录框、无恢复按钮 |
| WebGL 被模拟禁用 | 显示失败与兼容入口，点击后兼容地图可恢复 |

代码原因：

- client/core/campaign-api-client.js 的 request 无请求/响应体超时，也不保留 HTTP 状态用于区分会话失效和暂时故障。
- campaign-entry.js 的 boot 在已有令牌时等待状态 API，等待期间没有可交互的登录/重试界面；异常时不区分 401 与临时网络失败，直接清除令牌。
- client/map/map-loading-recovery.js 只有收到 campaign-ready 或已有 campaignBootstrap 才启动恢复计时。这两者都依赖入口模块和状态 API 成功，所以覆盖不到更早的启动失败。
- 登录入口依赖多个 ES 模块，其中一个加载失败即可阻止入口初始化。
- R11 普通地图 JSON 有超时重试，但 relief-field.js 的高程资源请求仍只有外部 abort signal，没有自身超时。该项为代码检查，未额外注入复现。

**判断：** 可独立复现的游戏缺陷；它会把网络异常放大成无提示卡死，但不能证明用户原电脑一定正好触发了此路径。纯 WebGL 不可用已验证有兼容恢复，不能仅凭手机能进就断定桌面显卡问题。

## 3. 服务端性能：有结构性阻塞，未复现整体不可用

环境：i7-12700K、约 32GB RAM、Node 22.17.1。60 个简化账号，每人33张卡、1块领地，初始无长期战报。不能折算正式服务器容量。

- 单独测量全服保存：10/30/60 账号平均约 39/103/201ms。
- 60 账号、5 场比赛时额外保存约263ms。
- 补充30秒混合测试：60玩家每5秒错峰状态轮询、5场比赛持续推进、每5秒持久化，并发检查健康接口和首页；没有 HTTP 错误。
- 混合测试全服保存平均271ms、最大288ms；事件循环最大停顿307ms；首页请求最大333ms；RSS约399MiB。
- 6次保存的分项采样：体能 prepare 共18次，累计约1145ms，平均每次64ms；JSON序列化及同步写盘共6次，累计340ms，平均57ms。体能在多阶段重复处理全体账号，是明确优化目标。统计为包含调用耗时，不代表完整 CPU 火焰图。
- 客户端与服务端处于同一个本地进程，受阻塞时客户端发起也会延迟，HTTP延迟不能完整模拟外部客户端排队；事件循环延迟单独测量。测试只有30秒，无公网/Nginx/长时间运行/真实存档/所有比赛类型压力覆盖。

代码边界：server.mjs 在同一 Node 事件循环提供网页、静态资源、API和比赛；JsonCampaignRepository 全量 JSON.stringify + 同步写盘/fsync；CampaignService.save 同步结算全体账号并刷新视野。只读 state 也可能触发结算与保存。浏览器每5秒获取完整状态，隐藏页会暂停，有 pending 防重入，但挂起请求因缺少超时可能长期占据 pending。

结论：性能风险真实存在，在更弱机器、更大存档和更高负载下可能加重问题；本次实验没有证明它造成正式站首页连接超时。

原始记录：outputs/access-audit-20260919/report.json、outputs/access-mixed-audit-20260919/report.json。

## 4. 在线管理与部署策略

- 同账号每次登录重写唯一 token。隔离复现：第二次登录后，首次 token 返回401，新 token正常。app.js 地图轮询静默吞掉401，旧设备可能留在过期状态；这解释会话异常，不能解释 TCP 连接失败，也尚未证实用户两端同账号。
- 部署模板使用单进程、Restart=on-failure、5秒重启间隔；Node heap768MB、MemoryHigh1100M、MemoryMax1400M。模板没有运行中 HTTP 卡死探测/事件循环监控。进程尚活但阻塞时，不能靠退出重启策略自动恢复。
- Nginx模板仅登录/注册限流3r/s、burst12，超限为429；未发现按桌面/手机区分的拦截规则。没有证据表明该限流触发本次故障。实际Cloudflare与Nginx线上规则尚未读取。
- 不应直接启用多进程/PM2 cluster共同写同一JSON文件；也不应仅提高代理超时或内存上限就宣称修复。

## 建议顺序与尚缺证据

1. 优先核对公网入口：同一电脑切换手机热点/同Wi-Fi对照；核对Cloudflare代理、WAF事件、源站连通及证书模式，关联失败时间。不要把固定Cloudflare IP当长期方案。当前没有修改任何CDN/DNS策略。
2. 补齐登录前独立恢复界面、API超时、401明确反馈；应覆盖入口模块失败和状态请求挂起。避免自动重试可能产生副作用的POST。
3. 为服务加请求耗时、事件循环延迟、保存耗时和RSS日志；核对实际生效systemd/Nginx配置及历史退出原因。
4. 再优化重复全服体能结算、同步保存和状态负载，保持经济/持久化事务边界；用真实规模隔离副本和更长混合测试验证。

需要事故时段的Nginx access/error日志、yellowdogs-rougelite systemd journal、CPU/内存/出网带宽曲线、OOM记录，以及Cloudflare相关事件，才能继续归因源站侧/边缘侧等待超时。没有这些记录不能宣布全部根因闭环。
