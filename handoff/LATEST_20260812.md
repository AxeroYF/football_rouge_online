## SQL 存储评估

- 完整评估：`docs/sql-storage-assessment-20260812.md`。
- 结论：切换 SQL 技术可行性高、长期收益高、短期风险中高；建议 PostgreSQL，不建议以 SQLite 作为最终正式方案。
- 当前本地单 JSON 约 61.98MB，其中归档约 40.26MB、比赛约 18.04MB；生产分片此前约 28GB、约 3850 个 revision，说明历史 revision 生命周期与全量内存加载已成为长期问题。
- 当前分片已经按脏作用域、账号卡牌、比赛报告和 NDJSON 流水拆分，但启动仍加载完整状态，保存仍有同步序列化/比较/`fsync`，SQL 的核心收益应来自行级事务、按需读取和索引，不是把整棵状态塞入一个 JSONB 行。
- 推荐“关系表保存钱包、卡牌、礼包、市场、邀请、邮件、比赛摘要；JSONB 保存比赛报告、直播 checkpoint、赛季归档”的混合模型。
- 保留 `YellowDogsLeagueService` 为业务层，增加 Repository + UnitOfWork；分片先作为权威，经过离线导入、影子写入、对账、灰度读和停服最终切换。
- SQL 不会自动降低 V2 模拟 CPU 或完整 `view()` 构建成本，这两部分仍需独立优化。

## 下一步建议

1. 用户先部署并验证最新 V2.1 平衡热更新，观察新比赛的阵型、控球、红牌和伤病数据。
