V4 默认启动及服务器压力评估　2026-11-18

npm start、npm run dev 和 npm run start:v4 使用 V4。YDL_V4_SCHEDULE=0 可启动旧版对照。远端镜像 Worker 应与主服使用同一版本。此次未连接云主机或用玩家存档开赛。

自动赛程和管理员提前开赛共用正式 V4 宿主。友谊赛、玩家房间及两回合对战、AI 训练、云端和外部 Worker 镜像批量赛使用同一 V4 内核，由实时适配器驱动原观看与结算接口。赛季总决赛的比赛工厂也已接线，赛事沿用现行停用设置。赔率保留原独立 V1 采样。V4 赛程遇到未支持的新增特性时在锁定前报告错误。实时对战战报另记录未实现的特性钩子。当前环境模型仍使用中性天气。

测试机为 Windows、i7-12700K、Node 22.17.1。Windows Job 将每组进程连同所有子进程约束为两个逻辑 CPU、2 GiB。两版使用相同赛季日期、16 队、首轮 8 场完整 90 分钟、隔离 JSON 存档。先 V3 后 V4 和先 V4 后 V3 各测一次。V3 按比赛切片推进并调用原结算；V4 包含 worker 生产、分段录像、队列、发布门槛与原结算。推进测试时钟跳过观赛等待。每组都核验了 8 份战报的实际引擎版本。

CPU 和操作系统 I/O 统计包括进程启动和子进程；传输量包含文件和管道等 I/O，净增量只统计最终留在测试目录的数据。进程组峰值提交内存不是整机物理内存。两次实验以单轮计算为负载，没有叠加 HTTP 客户端、镜像训练或云盘延迟。Windows Job 的 CPU 限制不能复现共享云主机的争抢。本轮 V4 的内存有余量，CPU 在产出录像期间接近占满两核。单轮在现行 20 分钟赛程间隔内完成。长期运行的容量取决于录像保留时间、真实存档增长和同期开赛数量。

既有第 50 阶段另测了 10 个混合活跃账号的 V4 负载。8 场在 140.68 秒内完成，业务 HTTP P95 为 64.99 毫秒，进程组峰值约 480.5 MiB。该值来自历史分片测试，与本轮 JSON A/B 对照的负载不同。
