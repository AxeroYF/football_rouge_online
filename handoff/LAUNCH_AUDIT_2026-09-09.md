现有部署文档指向 2 核 / 2GB 的 Ubuntu 服务器。建议今晚按限量测试开服，先邀请 10–20 人错峰进入，观察后扩容；这是运营建议，不是已验证的在线容量，也不是已经加入代码的并发限制。当前架构仍是单 Node 进程、内存世界、同步全量 JSON 持久化，不适合直接承诺大规模同时比赛。

### 生产力应如何发放

1 点生产力每分钟推进 1 点建设需求。训练中心首建需 400：总生产力 10/20/40 时，单项目约 40/20/10 分钟。两个同需求项目同时开工会均分生产力，各自时间翻倍，总工作量不变。

开服奖励建议使用现有“待分配一次性生产力奖励”，不要往已废弃的 resources.production 库存写 400。待分配奖励可投入一个建设项目；普通征服补给仍按原规则处理；新服 400 补给已支持保留未使用余量。生产力为 0 的出生地也可用补给完成首座训练中心。

### 每日改为 8 次后的经济变化

只统计成功占领普通中立地块；失败不扣次数但进入休整；玩家领土战争不占这个额度；豪门挑战独立收费且不占领地块。北京时间零点重置，奇观 +1 奖励仍叠加为 9。已用 5 次的旧账号会直接剩余 3 次，不清空当天记录。

按现有地块奖励分布估算，成功征服 8 块的期望奖励是：直接金币约 3,000、球迷约 360、珍奇包约 1.8 个、赞助合同约 2.8 份、一次性生产力约 160、研究进度约 112。这是大量地块的概率期望，实际每块奖励固定且可预览，并非每日保底；赞助还受槽位和到期限制。

开局总部 1 块加 8 块新地，共需 9,000 球迷满产。现有 5,000 + LV1 全天自然增长 2,400 = 7,400，即使计入平均征服球迷也只有约 7,760。这种欠利用会拖慢产出，建议将礼包总初始球迷提升到 8,000。

地图仅有 585 个普通地块，另 13 块为不可占领的豪门所在地。假设每人占 1 块出生地、所有人每天都胜利占满 8 块，20 人约 3.5 天、30 人约 2.3 天就会用完普通地块。实际受移动、接壤和战败影响会更久，但这提示：8 次是成长加速，不是无限长期内容。后续应安排战争外交、豪门挑战和联赛，而不能只靠持续发新地块奖励。

## 运营方向

- 首日目标：选地、配置远征与留守、建训练/球探设施、征服 2–3 块；8 次为上限，不设必须做满的奖励。
- 第 2–3 天：总部升级、资源偏好与球迷配置、形成第一套战术；引导低档豪门挑战及友谊赛。
- 第 4–7 天：赞助续签、设施分工、玩家交易、外交与战争；为联赛留出后续成长目标。
- 首周礼包总额控制在上述 50,000；先不叠加高额每日签到、排名金币奖或直接赠送 +3 传奇。故障补偿建议每次 2,000–5,000 金币，按实际影响名单补发并记原因。
- 每日看：新增/活跃人数、金币总量与人均中位数、各来源产币与消耗比例、金币不足导致的训练/挑战失败、征服数、球迷利用率、设施升级分布、赞助有效槽数、商店售罄速度、同账号群的异常交易。
- 当前金币账本仅保留最近 200 条，不能当作完整运营审计库。开服前后定时导出聚合快照；后续补追加式流水。建议指标触发复盘，而非当天反复改价：例如连续三天产币超过消耗 1.3 倍并且中位持币上涨，才讨论产出或消耗调整。

## 性能检查与已修复项

### 1. 多人迷雾缓存：已修复

原 FogSpatialIndex 是服务端和前端共享的 24 项几何缓存；全服轮流计算超过 24 种持地组合时，几何与可见地块不断重算。初次本机诊断中 30 账号全量结算约 2,574ms，状态构建均值约 87ms（当时与回归任务有短暂重叠，只作为问题诊断，不是严格容量基线；60 账号旧版测量因耗时中止）。

FogService 现在用 WeakMap 持有每个账号当前领地组合的可见地块结果，仅保留一个当前组合和临时海路预览。持地变化重新计算；预览结束清掉临时结果；总部共享、遭遇玩家和世界归属仍每次刷新，权限规则未放宽。测试覆盖 40 账号反复刷新、持地变化、原有外交共享/撤销/迷雾行为。

### 2. 同步持久化：已减少体积，架构风险仍在

移除全量 JSON 缩进；原子临时文件、fsync、rename、事务回滚保持。60 个新账号无战报场景从约 7.09MB 减为 3.54MB；5 场进行中的比赛约第 10 分钟，样本从 14.88MB 减到 6.85MB（比赛种子不同，属于近似体积比较）。

每次经济结算仍遍历全部账号和地块，所有写入仍阻塞 Node 主线程。不要用 PM2 cluster 或多容器共享这个 JSON 来“利用双核”，会产生相互覆盖。中期路线是：事务型数据库保存账号和经济流水；战报独立存储；比赛模拟放 worker，保留服务端单点权威结算与幂等。

### 3. 状态与前端：已减无效开销

状态里的资源视图由重复两次改为一次计算。地图页面仍每 5 秒轮询，但后台标签停止请求，恢复前台即同步。后续进一步拆分稳定目录、玩家资料与动态状态，使用版本号/差量或按事件刷新。

已有优化包括地图按需重绘、像素比上限 1.5、隐藏页不绘制、地形瓦片/模型按视野加载、阴影按变化更新、地图资源 hash 缓存和 gzip、静态文件流式发送。地图主要消耗玩家设备 GPU 和首屏带宽，不是服务器替玩家渲染；弱服务器最应处理的是逻辑 CPU、I/O 和出网流量。

机器为 i7-12700K、约 32GB RAM、Node v22.17.1；部署包采用另一 Node 运行时。每账号 33 张卡、1 块地、无历史战报。真实服务器的 CPU、磁盘、网络和长期存档都可能更慢。下表不能直接换算上线承载人数。

## 今晚优先级与后续路线

**今晚必要：** 确认初始金币替换方案；重新打包；单进程启动；确认 Nginx gzip 与登录限流生效；核对 data 目录与权限；备份后用两个测试账号在服务器走一次建队、购买、训练退款、普通征服、豪门领取和重启恢复。当前备份脚本会短暂停服，安排在维护窗口。不要将旧测试世界/旧会话当成新服世界直接发布。

**先小范围观察：** 建议以接口 P95 <500ms、事件循环 P95 <100ms、RSS <800MiB、持续 CPU <70%、无 5xx 和无存档失败作为扩邀前的观察线。这些是建议阈值，项目当前没有完整自动监控/自动限流落地。服务器需要至少 30 分钟“玩家轮询 + 同时比赛 + 经济存档”的混合测试，再决定并发上限；本机结果不能代替这一步。

**下一阶段优先：**
1. 建立全服比赛准入与排队，在创建比赛/扣费之前拒绝超载；保留退款和重试语义。

3. 登录密码计算目前使用 scryptSync，会阻塞主线程；改异步并限制排队数，保留已有密码兼容。
4. JSON 存档迁移到事务存储，战报归档；外交 requests/receipts 和豪门请求幂等记录需要有可证明安全的保留策略，不能直接删除后允许旧请求重放。
