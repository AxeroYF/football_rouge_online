# 黄狗风云后续路线图与 Admin 平台规划

更新时间：2026-08-29（Asia/Shanghai）

> 历史规划提示：Admin 规划保留参考，但当前总路线和优先级已转移至 ROADMAP_2026-08-31.md。

## 总体判断

黄狗风云不是 S4 联赛模式的简单延伸，而是以持续世界、地块征服、球队养成和设施经营为核心的类文明游戏。因此 Admin 平台不应整体照搬 S4：保留成熟的账号、内容、比赛审计与安全框架，把 S4 的联赛控制中心替换为世界运营中心。

当前代码仍处在适合建立边界的早期阶段。下一阶段应优先补齐 Admin 与数据基础，再继续扩展征服、设施和经济玩法，避免每增加一个系统就产生新的临时管理入口和直接存档修改流程。

## 推荐开发阶段

### Phase 0：Admin 与数据基础

- 独立的 Admin 登录、会话和 RBAC，至少区分只读、运营、内容和超级管理员。
- 所有管理写操作记录管理员、原因、时间、操作前后摘要和唯一 `adminActionId`。
- 建立金币、道具、球员卡、挑战次数等资源流水，不以直接改余额作为正式操作方式。
- 建立统一后台任务模型，承载建造、球探、训练、伤病、体能恢复及未来赛季任务。
- 建立配置版本、功能开关、批量操作预览、确认令牌、幂等键和可恢复备份。
- Admin 只能通过应用服务修改状态，不允许直接编辑 `campaign-accounts.json` 或世界 JSON。

### Phase 1：征服核心闭环

- 接入联赛、征服、被动防守三套阵容；球员体力与伤病是同一份共享状态，不因阵容切换而刷新。
- 实现 AI 与玩家挑战的独立每日次数、失败冷却、体力损耗和挑战状态锁。
- 玩家挑战玩家时先预扣金币，失败后向防守方结算赔偿，成功或取消时按明确规则结算托管资金。
- 所有主动进攻的两回合默认都视为客场；防守方获得主场加成。
- 跨海挑战根据距离在赛前扣除体力，基础航海距离为 500 公里，港口改变距离与消耗。
- 同一玩家不能并发挑战多个地块，同一地块也不能被多个挑战重复占用。
- 保存可审计的挑战历史、领地变更历史和失败惩罚记录。

### Phase 2：设施效果落地

建议按依赖顺序接入：

1. 港口：提升航海距离、降低跨海体力消耗。
2. 体能恢复中心：提升驻扎球队恢复速度。
3. 医疗中心：管理并缩短伤病周期。
4. 球探中心：定时产出三选一球员卡或可入背包的球探包，加入国家权重和极低传奇概率。
5. 训练中心：为分配球员提供 26 项能力的随机成长，等级影响成长量和核心属性权重。
6. 俱乐部商店：提供持续金币来源。
7. 主体育场：承载首都、主场和后续容量/收益/防守效果。

所有设施应复用 Phase 0 的统一任务、领取和流水模型。当前测试规则仍为一级统一 5,000 金币、施工 60 秒、暂不开放升级。

### Phase 3：球员卡、背包与经济循环

- 建立背包、球员卡包、三选一领取、球员强化、工资和设施收入。
- 所有金币来源与消耗进入可查询流水，支持运营分析金币产消比、存量分布和通胀。
- 明确破产、欠薪、退款、补偿和异常回滚规则。

### Phase 4：玩家领土战争

- 被动防守使用可复现的阵容快照，避免玩家离线时阵容状态不明确。
- 增加新手保护、连续受击保护、挑战冷却、赔偿上限和防小号输送规则。
- 首都失守后进入流浪国家状态；有可用领地时重新选择首都，没有可用领地时淘汰并封存账号。
- 领地转移、首都变更、建筑保留/移除和淘汰均需完整审计。

### Phase 5：领袖技能

- 用数据驱动的“触发器 + 条件 + 效果”模型实现，避免把技能逻辑散落在各服务中。
- 首批只做 8–12 个简单、可观察、容易平衡的技能，覆盖建筑槽位、航海、主客场、经济、球探和恢复。
- Admin 支持技能配置、启停、版本、使用率和胜率统计。

### Phase 6：赛季与运营活动

- 增加赛季目标、世界事件、排行榜、活动配置、补偿邮件和赛季归档。
- 赛季重置必须与账号资产、领地、建筑和荣誉的保留规则解耦。

### Phase 7：生产环境扩展

- 多人公开测试前，将当前单体 JSON 存档迁移到支持事务的数据库；生产推荐 PostgreSQL，本地可保留轻量数据库方案。
- 对挑战、领地、金币和建筑任务引入事务、唯一约束和分布式锁。
- 补齐健康检查、告警、备份恢复、容量评估和负载测试。

## S4 Admin 功能取舍

### 保留并适配

- Admin 登录、会话、限流和操作审计；移除硬编码默认密码。
- 运营概览、玩家检索、账号详情、比赛详情和赛果审计。
- 金币增减、补偿与回收，但必须填写原因并形成不可变流水。
- 封禁、登录冷却和账号状态管理。
- 全服/定向邮件与运营公告。
- 球员数据、特性和球员卡原画管理。
- Excel 导入导出及导入前差异预览。
- 阵型、战术和平衡分析，并扩展地图、跨海、设施和领袖技能维度。

### 移除或后置

- S4 手动联赛模拟、联赛开始/重启/每日重置和杯赛控制。
- 投注审计。
- 33 人阵容强制清理、X 球员成长发放等 S4 专属工具。
- S4 卡包发放；改造成球探包、道具包和补偿包。
- 冠军徽章暂缓到赛季系统。
- 教练工作室改造成领袖技能工作室。
- 不复制“强制解散并重新分配全部资产”；改为账号封存、领地释放、资产处置预览和二次确认流程。

## 新 Admin 信息架构

1. 运营概览：在线、活跃、挑战、经济、异常任务和系统健康。
2. 玩家与球队：账号、阵容、球员、体力、伤病、背包、金币和处罚。
3. 世界地图：领地归属、首都、流浪/淘汰状态、保护期和领地修复。
4. 挑战中心：进行中比赛、锁、赛果、失败惩罚、托管金币和异常结算。
5. 设施与任务：建筑、施工、球探、训练、医疗、恢复和任务补偿。
6. 经济：金币流水、来源/消耗、工资、设施收入、通胀和异常转账。
7. 内容工作室：球员、特性、领袖技能、卡包、配置和活动。
8. 系统与审计：管理员、RBAC、配置版本、功能开关、审计日志、备份与迁移。

## 推荐代码边界

```text
Admin UI
  -> Admin Query API / Admin Command API
  -> AdminService
  -> EconomyService / ChallengeService / BuildingService / 后续领域服务
  -> Repository + Audit Log
```

- 查询与写入接口分离；高风险写操作必须预览和确认。
- 发放资源、领地修复和任务补偿必须幂等。
- 任何批量操作先返回影响范围，再由确认令牌执行。
- AdminService 负责权限和审计，领域服务继续负责业务约束，避免后台绕过游戏规则。

## 当前最推荐的下一步

先完成 Phase 0 的最小骨架：Admin 身份/RBAC、审计日志、资源流水和统一任务模型。随后进入 Phase 1，把三套阵容、共享体力、次数限制、失败惩罚、PvP 金币托管和挑战锁组成完整的征服闭环。设施效果应在这两个基础稳定后按依赖顺序逐个接入。
