## 一、当前起点

黄狗风云已经进入小规模公网测试。下一阶段目标是让玩家能稳定完成“获得球员 → 培养与编队 → 出征比赛 → 获得资源 → 发展领地与设施 → 再次出征”的循环。

| 模块 | 当前事实 | 后续重点 |
| --- | --- | --- |
| 服务器 | 用户已在 Ubuntu、2 核/2GB/40GB、106.54.12.175 部署 V0.1，可以进入游戏 | 实测稳定性、并发结算、备份恢复和发布回退 |
| 最近本地优化 | 地图压缩/缓存/并行加载、登录及地图加载 R3 背景已修改，尚未打包上线 | 保留待发布清单；等明确授权再发布和公网验收 |
| 开服选人 | 33 人、四个位置池、只有门将至少 3 人；概率 C30/B40/A25/S5 | 弱网恢复、流程理解、初始阵容平衡 |
| 球员管理 | 回收、市场挂牌/购买/撤回、汰换已形成；后台代办金币交易已有 | 并发、状态边界、经济闭环、记录可追溯 |
| 培养与战术 | 强化、训练、特性、远征/留守、战术板及属性显示已有 | 保持显示与比赛一致，补实际对局和平衡验证 |
| 地图与比赛 | Three 地图、迷雾、移动/海路、地块挑战、两回合比赛、电视台已有 | 完善征服后发展目标、连续出征限制、胜败保护 |
| 设施 | 七类设施可配置；球探、训练已有主动功能；建造/槽位/地图展示已有 | 其余设施实际效果、升级任务、拆除；upgradesEnabled 当前仍为 false |
| 体力/伤病 | 比赛内已有相关概念；完整赛后持久化、服务器时间恢复和设施联动尚未形成 | 将已存在的比赛状态接到长期经营中 |
| 经济 | 金币、征服奖励、卡包、养成与交易入口已有；初始金币仍是 1,000,000 | 区分测试资金和正式节奏，统一资源投放/消耗测算 |
| 新特性 | 已有 16 张候选提案，仍待审阅，未加入正式池 | 审机制、验证引擎、分批投放 |

注意：capabilities 标签、升级价格数组、已有接口骨架，不等于设施效果已经落地。属性与特性已有共享契约和回归，例如 996 固定体力 94；应先核查差异，再决定是否需要进一步整理，不能把它们当作完全未实现而重写。

## 三、M0：把线上测试稳定下来

### 工作范围

- 建立线上问题清单：发生时间、版本、操作步骤、影响账号、预期和实际结果；不收集明文密码。
- 对当前已经存在的玩法做一次完整联测：登录/建队 → 编队 → 训练/强化 → 出征比赛 → 领取奖励 → 回收/挂牌/汰换 → 重启恢复。
- 特别检查两人同时购买同一挂牌、重复点击回收/汰换、任务结算前后断线、比赛中修改球员、重新登录后的恢复。
- 地图区分冷启动、普通再次进入、强制刷新，记录下载量、可操作时间、长任务和错误；区分网络等待与客户端渲染耗时。
- 对这台测试服务器分档增加请求及同时比赛数，观察响应 P50/P95、事件循环延迟、内存和存档耗时；以实测决定可承受规模。
- 现有原子写入、坏档报错、正常停机保存继续保留。补备份保留策略与一次真实流程的隔离恢复演练，检查恢复后任务是否重复结算。
- 规划专门的增量更新流程：版本/文件清单、校验、数据兼容说明、备份、停服更新、健康检查、回退；当前 install.sh 仍只做首次安装。
- 后台补充测试需要的可观测状态及操作记录，复用已有权限和审计。测试账号重置如需开发，必须限定账号与范围，不以全服清档解决问题。

### 验收标准

- 至少完成一轮连续 24 小时的小规模联测，无未解决的丢档、重复结算或阻塞核心玩法的问题。
- 从备份恢复到隔离环境后，账号、球员、金币、任务和世界状态相符。
- 有可执行的更新/回退说明，并能区分“本地已完成”和“线上已生效”。

本轮地图和登录优化已在本地完成，不再列作从零开发；需要用户明确要求打包后才进行线上验收。

## 四、M1：先确定经营规则，再接入新效果

这一阶段拆成规则设计、数据核查、逐项实现三步。此前大任务已回退，不能直接恢复那一整套代码或数值。

### 1. 球员属性与状态一致性

- 核查卡面、详情、编队、训练、强化、战术板、AI 选人和比赛快照的最终属性是否一致。
- 区分“耐力属性”和“当前体力状态”；优先沿用现有引擎体力概念，不新增士气值。
- 建立状态操作矩阵，覆盖训练、远征、比赛、挂牌、伤病、强化、回收和汰换之间的允许/禁止/暂挂关系。
- 保留目前已确认的规则，包括远征卡可以挂牌、撤回回原编队、比赛运行中采用既定快照等。
- 新伤病跟随球员实例；挂牌、转队和撤回不能意外清除伤病或重置恢复时间。具体可交易/可训练边界在设计时列明。

### 2. 金币与球员产出总表

把现有规则先列完整，再提出调整，不能直接降低线上余额或改动已确认价格。

| 分类 | 需要纳入测算 |
| --- | --- |
| 系统投放 | 初始金币、中立挑战奖励、卡包、球探、未来地块/设施收入 |
| 系统回收金币 | 球探、强化/保卡、建造/升级、未来治疗或恢复服务 |
| 玩家间流转 | 市场成交、后台代办交易；玩家之间转钱本身不是系统回收金币 |
| 球员产出 | 开服选人、开包、球探、比赛/活动奖励、汰换 |
| 球员消耗 | 强化副卡、回收、汰换素材 |

建议先模拟新手、普通活跃、重度活跃三种玩家的 7 天及 30 天收支。重点检查卡包/球探产出与回收价、挂牌最低价、强化成本之间是否形成重复套利，以及升级要积累多久。100 万初始金币目前适合功能测试，正式起步资金应单独评审。

保留现有已确认的回收、最低挂牌价与汰换规则作为测算基线；发现冲突先说明影响，再提出成套调整。

### 3. 中立远征体力与胜败规则

先完成中立地块版本，后续玩家地块复用其基础：

- 列出移动、第一回合、第二回合、加时、胜利、失败、中止分别消耗/结算什么。
- 明确胜利后的驻扎位置、首次/重复奖励；失败后的退回位置、再挑战冷却；中途断线不能绕过惩罚。
- 两回合之间已有等待时间，与战败后再次挑战冷却是不同规则，分别展示和配置。
- 保留当前已确认的己方领地移动规则；新增成本必须作为玩法改动单独说明。
- 体力自然恢复用服务器时间计算；离线回来和服务器重启后结果一致，且不重复恢复。
- 防止体力不足形成新手死局：需要可理解的自然恢复和轮换路径。

### 4. 服务器时间伤病

- 明确哪些比赛事件产生伤病、何时写回、伤病类型与持续时间区间。
- 采用服务器绝对恢复时间，不沿用 S4 的比赛场次倒计时，也不由浏览器计时决定是否痊愈。
- 允许长时间伤病存在，但同时评估初始阵容、替补供给和自然恢复，避免玩家只能等待。
- 比赛已经确认的结果只写回一次；治疗任务和自然恢复到期相遇时也只结算一次。
- 界面只显示必要的伤病状态、剩余时间与治疗入口，详情再解释原因。

### 验收标准

连续完成数轮“征服—奖励—养成—轮换—再征服”，体力、伤病、金币和球员实例均可追溯。断线和重启后结果一致；卡片、状态和比赛的数值一致。

## 五、M2：让七类设施有实际用途

先做通用升级/拆除规则，再分批接入。建议首轮完整开放 LV1–LV3；LV4–LV5 在经济验证后扩展，不直接沿用旧价格数组作为最终路线。

| 设施 | 建议主要作用 | UI 重点 |
| --- | --- | --- |
| 训练中心 | 延续主动训练，升级影响容量或可选择的培养方向 | 席位、当前任务、结果、升级前后对比 |
| 球探中心 | 延续主动发掘，升级增加选择能力或投放质量 | 位置/地区选择、概率、进度和候选 |
| 俱乐部商店 | 可预测的金币收益 | 收入速度、结算上限/规则、最近收入 |
| 体能恢复中心 | 改善自然恢复，是否提供主动恢复另行定规则 | 当前恢复效果、作用范围、剩余时间 |
| 医疗中心 | 伤病后的治疗选择 | 床位、球员、费用、自然/治疗恢复时间对比 |
| 港口 | 影响本港出发的航程、耗时或补给选择 | 当前航线与建设后的差异 |
| 主体育场 | 俱乐部经营或主场特色 | 发展状态、已生效效果与下一等级变化 |

港口的新规则只对规则生效后发起的行动应用，避免正在海上的队伍被更新卡住。主场效果如果影响比赛，必须确认引擎如何接收；不能只在界面写百分比。

### 升级与拆除共用规则

- 每级效果、费用和耗时要明确；没有实际效果的等级不开放升级。
- 同一建筑同时只执行一个建设/升级任务，说明施工期间旧效果是否继续生效。
- 拆除前显示收益损失、任务影响和退款，退款公式待经济表评审，避免建造/拆除套利。
- 训练、球探、医疗任务占用时，拆除应有明确处理路径，不能遗留悬空引用。
- 永久主场建议不开放普通拆除入口；其他设施的拆除按用户最终规则实施。
- 被动效果明确同类叠加、作用范围和失去领地后的变化。
- 离线金币按所有权与设施生效时间分段结算；换主、升级和重启不能重复领取。

### 建议批次

1. 升级/拆除基础 + 训练/球探升级 + 商店基本收入。
2. 已有体力/伤病规则接入恢复中心和医疗中心。
3. 港口与主体育场的战略效果；最后扩展高级路线。

### 验收标准

每座可用设施都有真实服务端效果，UI 能看到当前作用与升级差异。不同建设顺序形成取舍；拆除、任务结束、占领变更和离线恢复不会多发资源或丢球员。

## 六、M3：完善已有玩家地块挑战

已有玩家地块挑战基础，这一阶段补规则而不是重做一套比赛系统。

- 建立胜利、失败、撤退、取消、系统异常的结算表。
- 明确防守阵容何时快照、离线防守行为、比赛中可进行的养成/挂牌操作。
- 确认攻方驻扎/退回位置、领地归属、资源托管或赔偿、冷却和受攻击保护。
- 完善同一地块同时被多人挑战、连续攻击同一玩家、目标归属中途变化的处理。
- 保护永久主场及新玩家的方式先评审，避免扩张领先者持续压制其他人。
- 战报保留阵容快照、结果、领地与资源变化，以及服务器结算标识，后台可追溯争议。
- 排行榜和荣誉可在规则稳定后接入，不先用大额金币胜利奖励放大滚雪球。

验收：两名玩家在线/离线组合及多人竞争目标均能完成攻防；一次挑战只产生一次归属与奖励变化。

玩家之间的直接金币交易继续只保留后台代办入口；玩家端开放另行决定。

## 七、M4：增加长期目标与构筑内容

- 先做一组地区目标或 AI 据点链，复用现有地图和挑战，不扩大大陆范围。
- 验证地区征服、球员收集、阵容构筑之间的关联，再增加地区杯赛或周目标。
- 对现有 16 张特性候选先评审机制，再挑少量接入；每项需能在引擎事件、球员详情与战报中解释。
- 用对局模拟检查触发频率、叠加、持续时间与收益；先利用已有引擎事件，新增机制单独评估。
- 卡包、球探、强化特性、地区奖励的投放一起测算。
- 补充管理员创建活动、发奖和查询异常的入口，所有修改可审计。

验收：玩家有数天至数周的清晰目标，不同阵容/设施布局具有实际差异；不靠单纯延长等待制造内容。

## 八、M5：长期运行和正式入口

- 完成 HTTPS 与 yellowdogsleague.online/versus/ 的路径适配；当前根路径 API/资源引用需要配套修改，不能只改反向代理。
- 为更新包建立可核验的版本号、变更清单、兼容范围与回退说明。
- 建立备份轮换、磁盘容量管理、故障日志和运行指标；扩大数据量后再据实评估持久化方案。
- 当前先保留单 Node 进程；如果比赛计算或同步 JSON 存档成为实测瓶颈，再设计对应的计算隔离或数据迁移，不直接堆多副本写同一存档。
- 完成新手流程、手机横屏适配、长时间游玩及网络中断恢复验收。
- 安卓封装作为可选后续交付，以 Web 玩法和更新流程稳定为前提。
- 赛季、重置范围、继承内容尚需决定；没有明确方案前不做清档或赛季迁移。

## 九、近期建议执行顺序

1. 持续归档公网测试问题，优先消除阻塞和资源/存档异常；维护本地待发布清单。

## 十、开发约定

- 每项玩法改动先形成可审阅的规则、边界、关键界面及验证范围；逐项落地，避免一次性加入大量相互依赖的未确认数值。
- 不引入士气值，不自动恢复已回退的设施/体力/经济整套方案。
- UI 延续现有风格，主页面展示操作、状态、结果；详细说明放在需要时查看的位置，不堆冗余小字。
- 保留远征/留守两编队、已确认的球员卡规则及服务器时间方向。
- **只有用户明确要求时才打包或部署相关准备；本次仅编写路线图，不生成任何发布包，不修改玩法或真实数据。**
